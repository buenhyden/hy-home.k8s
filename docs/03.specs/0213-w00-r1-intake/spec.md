# W00 r1 Intake and Residue Correction Technical Specification (Spec)

## Overview

This change contract records the 2026-11-13 r1 revision of the external v14.7 execution package (`_workspace/workspace_execution_tasks_v14_7_revision_20261113_r1/`, called PKG below) in the repository's own records, and corrects the residue records that the r1 W00 prompt and the user's decisions of 2026-11-14 (W03-D77 to W03-D82) show to be wrong or missing. The [Plan](plan.md) orders the work and the [Task](tasks/tsk-0001-w00-r1-intake.md) records execution.

## Core Design

[AD-0006](../../02.architecture/descriptions/0006-workspace-agent-governance-platform.md) owns the governance view and [ADR-0060](../../02.architecture/decisions/0060-work-residue-ledger-amendment.md) the ledger; neither changes. The ledger holds pointers (identity, kind, state, owner, resume condition, source) and the Task holds the residue text, evidence and acceptance. No table of this package is a second ledger or a progress record: the classification table is analysis of residue and is replaced by the closing report, and the seeds are residue.

## Data Modeling & Storage Strategy

No schema, registry key or code changes. Ledger data: up to seven entries added (the W04 row and any uncovered `shared_contract` field may reduce or add one), two deleted after their terminal pass (fewer if a read is not evidenced), twelve entries edited in place, thirteen if the W00-H01 owner edit applies (W03-H02, GOV-04, R147-03, OPEN-01, OPEN-02, OPEN-03, OPEN-04, OPEN-06, W03-H15, W03-H29, SDLC-07, R45-12); counts are read before and after and the gate result is recorded (expected at draft with seven seeds: 76 entries before, 81 after; live rows 83 before, 90 after, 9 terminal).

## Interfaces & Data Structures

The gate `scripts/validate-work-residue-ledger.py --root .` and the schema `docs/99.templates/contracts/work-residue-ledger.schema.json` are unchanged consumers. The new tables sit under `## Task Evidence` of the SPEC-0161 Task after `Residue Handoff`.

## Edge Cases & Error Handling

- A seeded ID collides with an ID another package took before this one lands: re-read the next free number at commit time and rebase.
- The v14.7 root reappears with other bytes: the Task records both and keeps the r1 root as PACKAGE_ROOT.
- The r1 root is moved or renamed: hashes, not paths, identify the input; the Task states the path it read.
- A closure's PASS would read as more than its read or survey: the `Location` cell states what the PASS records and nothing beyond it.
- A ledger entry or live row edited alone is refused by the gate as `RESIDUE-DRIFT`; the pair is edited in one step.
- Another package changes the live table before this one lands: rebase, re-count, and re-classify rows it changed.

## Failure Modes & Fallback / Human Escalation

If a current document or ledger value contradicts a row to be written, the author stops and asks the user and does not edit the value. If the survey cannot show that SPEC-0166 read and edited a file named in W01-H01, that row stays open. If a seed would need an invented fact (an approval, a date, an owner not in the sources) it is not written. Rollback is the revert of the implementation commit; before that, delete the package commit.
