# W03 Task Form Technical Specification (Spec)

## Overview

### Intent

This approved change contract is the sixth phase-3 package of the W03 stage of the external v14.7 execution package; W03-D49 puts the Task role after the Spec and Plan roles of SPEC-0200. It gives the Task role its COMMON-DOC-FORM-1 1.0.0 form in the Stage 99 registry, gives the Task template its TemplateDefinition with the full record that SPEC-0196 checks (W03-H13), and moves the template and every Task in the tree to the form (W03-H02). It applies W03-D01 (the evidence rules keep every recorded row value across the move), W03-D04 (the Task's `Lifecycle Traceability` is a registered local H3 under Execution Log) and W03-D50 (the SPEC-0161 Task moves form-only by a heading map and 13 of the H3 under its evidence H2 become H4), recorded in the [SPEC-0161 Task](../0161-w00-v14-7-delta-intake/tasks/tsk-0001-w00-v14-7-delta-intake.md). Recorded Task rows never change: no evidence row, work row or decision row of any Task differs by one byte after this package, and of a recorded table only the header line of the evidence table changes, by a recorded header map. A read of `main` at `a8c689e5` found one Task in the tree, the SPEC-0161 Task (121 KB, `completed`, 55 evidence rows, 14 H3 under `Task Evidence`). `sdlc/task` requires seven H2; its body contract reads `Lifecycle Traceability` under `Task Table`, and its `task_execution` binding names `Task Evidence` and `Criterion Acceptance`. Four scripts hold the 32 `TASK-` rule identifiers. One reader does not go through the registry: `task_base_evidence_rows` in `scripts/validate-links-and-owners.py` reads the literal `## Task Evidence`, and `scripts/validate-document-lifecycle.py` calls it on six lines for the base rows, the proposed rows and the first-record approval receipt of a new package; the same module reads a base Task's work rows with the proposed registry's profile. If the form were bound with those readers unchanged, the commit that moves a Task would report every recorded evidence row as deleted and skip `TASK-ITEM-DELETE`, `TASK-ITEM-HIDE`, `TASK-ITEM-EDGE` and `TASK-ITEM-RESET`, and every later commit would find no evidence row on either side, so `TASK-EVIDENCE-RETENTION` would compare nothing and pass while the approval receipt of a new package was never found. On 2026-11-14 the user decided the three choices this package raised (W03-D61): the evidence table keeps its nine columns and their names; the `Residue Handoff` table is a registered local H3 under Verification Evidence, so only the registry changes and the table stays in place; and the `Approval and Safety Boundaries` block moves whole under Scope > Inputs and Authority with the template check re-pointed. A requirement audit then compared the package with the W03 prompt, the task file `tasks/TASK-hy-home-k8s-W03.md` of the v14.7 package, and the user resolved its findings on 2026-11-14 with `W03 프롬프트에 작성된대로`, as written in the W03 prompt (W03-D65). One finding changes this package and supersedes the first choice of W03-D61: the evidence table takes the common column names of lines 307 and 739, and line 37 keeps a further column only as a registered conditional extension with its condition, owner, verification, review and removal. This package's commit records the W03-D61 row in the SPEC-0161 Task; W03-D65 is recorded there by the SPEC-0193 package commit. W03-D66, recorded by the SPEC-0207 package commit, binds each registry change to a bump level, and this package's is MAJOR, as the Contracts state. The [Task](tasks/tsk-0001-w03-task-form.md) records execution and the [Plan](plan.md) orders the work.

## Behavior Contract

### Normal Behavior

Contracts:

- **Task form.** `common_forms.forms` gains the Task form exactly as COMMON-DOC-FORM-1 1.0.0 defines it (`roles[5]`): `form_id` `task`, `title` `Task`, Scope (Objective and Parent, Inputs and Authority), Execution Log (Work Performed, Blockers and Decisions), Verification Evidence (Results, Resolution Links), Acceptance Decision (Criterion Decisions, Remaining Conditions) and Handoff (Promotion Receipt, Next Owner), every section required and `link_only` false everywhere. Templates keep their H1.
- **Column extension (W03-D65).** A new extension kind, `local_columns`, registers the columns that a role's table carries beside the common ones. `task-evidence-local-columns` names the table `Results` and the columns `Work Unit`, `Location`, `Required` and `Resolves`, with the five fields line 37 asks for: its condition (a Task whose evidence the acceptance and resolution rules of this repository read), its owner, its verification (`TASK-EVIDENCE-WORK`, `TASK-EVIDENCE-LOCATION`, `TASK-EVIDENCE-REQUIRED`, `TASK-EVIDENCE-RESOLUTION` and `TASK-EVIDENCE-UNRESOLVED`), its review (when the Task form or the common Task table changes) and its removal (when the common contract names the column or the rule that reads it is retired). The registry check refuses a column of that table that is neither a common name nor registered in the extension.
- **Local extensions (W03-D04, W03-D61).** Two registered conditional local H3: `Lifecycle Traceability` under Execution Log (`task-lifecycle-traceability`), verified by the body-contract check, and `Residue Handoff` under Verification Evidence (`task-residue-handoff`), verified by the work residue check of SPEC-0191. Each records its condition, owner, review and removal as for the other forms.
- **Profile and binding.** `sdlc/task` and its template twin keep `document_role` `task` and carry empty H2 lists. The body contract reads section `Execution Log` and table heading `Lifecycle Traceability` instead of `Task Table`. The `task_execution` binding reads `Verification Evidence` instead of `Task Evidence` and `Acceptance Decision` instead of `Criterion Acceptance`; each reader still takes the first table of that H2, which is the evidence table under Results and the decision table under Criterion Decisions. The evidence columns of the binding take the nine names of the Tables clause; the acceptance columns, the work-row columns, result states, acceptance states, the summary rule, enforced statuses and link columns do not change. The registry check refuses a binding whose evidence or acceptance section is not a required H2 of the role's form, so a later rename cannot leave the binding pointing at nothing.
- **Rules stay active.** Every `TASK-` rule that is active before this package is active in every commit of it and after it.
  - `task_base_evidence_rows` takes its section from the `task_execution` binding of the registry it is given and keeps the literal `## Task Evidence` only for a registry that has no evidence binding, which is the history from before the binding existed.
  - Each side of a comparison is read with its own registry: base rows with the registry of the base, which the cumulative-history check obtains with `registry_at(commit)` for the parent, and proposed rows with the proposed registry. This holds for the evidence rows, for the work rows that `TASK-ITEM-DELETE`, `TASK-ITEM-HIDE`, `TASK-ITEM-EDGE` and `TASK-ITEM-RESET` compare, and for the first-record approval receipt.
  - A Task that had recorded rows at the base and shows none under the proposed registry fails `TASK-EVIDENCE-RETENTION` or `TASK-ITEM-DELETE`; it never passes because nothing was found.
  - The readers change before the registry binds the form, and both land in one commit, so no commit holds a bound form with a rule switched off.
  - A staged-mode test proves the two-registry read where it matters most, in the commit that moves a Task. In a temporary repository the base commit holds the old registry and an old-form Task with recorded rows, and the index holds the registry with the form bound and the moved Task. The base registry is read from the base commit, not from the working tree: with identical rows the staged check passes, with one edited recorded evidence cell it fails `TASK-EVIDENCE-RETENTION`, and with one removed work row it fails `TASK-ITEM-DELETE`.
  - A first test shows the defect: with the form bound and the readers unchanged, an edited recorded evidence row in a later commit passes. Tests that stay in the suite then show, on the repository registry and for a Task in the form, one failing case for each of `TASK-EVIDENCE-RETENTION`, `TASK-ITEM-DELETE`, `TASK-ITEM-HIDE`, `TASK-ITEM-EDGE`, `TASK-ITEM-RESET`, `TASK-TERMINAL-EVIDENCE`, `TASK-DISPOSITION` and `TASK-PARENT-APPROVAL`, one for each of the `TASK-EVIDENCE-`, `TASK-EXECUTION-` and `TASK-ACCEPTANCE-` families of the profile validator, and the first-record approval of a new package found in the form and refused without its receipt.
- **Registry Schema Version (W03-D66).** SPEC-0207, which lands right after SPEC-0191, makes `schema_version` a SemVer string and binds every later registry change to the bump rule of lines 877 to 882 of the W03 prompt. This package's expected level is MAJOR. The column extension widens the closed `kind` enumeration of `form_extension` in the schema, which holds `local_h3` and `retained_form` at `a8c689e5`, and gives the extension keys for its table and columns in an object that admits no other key; the schema of the version before it refuses a registry that carries either and its typed loader knows only the two kinds, and an added key is MINOR only when every consumer tolerates it (line 878, W03-D66). The other registry edits of this package, the form, the local H3 extensions, the emptied lists, the moved body contract and binding, the mapped column names, the TemplateDefinition and the `work_residue` host, change values under keys that exist and would be NO_CHANGE on their own. One release unit takes its highest level once (line 882), so the implementation commit raises the MAJOR number of the version then on `main` by one and sets MINOR and PATCH to 0, in the registry and in the `const` of the schema, sets `REGISTRY_MAJOR` in `scripts/document_authority.py` to the new number, appends that number to `READABLE_REGISTRY_MAJORS`, and sets the guard's standard-library copy `DOC_REGISTRY_MAJOR` in `scripts/provider_write_guard.py`, all in that one commit. No other place holds the number. The tests of SPEC-0207 that pin the version read these constants, and its consistency test compares the guard's copy with `REGISTRY_MAJOR`, so this package edits no test for the bump and those derived tests are its check. A registry of the earlier MAJOR at the current path is then refused, and an earlier commit is still replayed with its own typed reading through `registry_at`, because its MAJOR stays in `READABLE_REGISTRY_MAJORS`. The Task records the level, the reason and the value before and after as evidence.
- **Header map and the rules (W03-D65).** Rows are read through the header map. A side whose registry binds the old column names is read by those names, and its rows are carried under the current names before any rule compares them. `TASK-EVIDENCE-RETENTION`, the evidence rules, the completion check and the first-record approval, which finds its receipt by the `Command` cell, therefore see the same cells before and after the rename, and the four `TASK-ITEM-` rules read the work rows, whose columns do not change, through the same two-registry read. A row that lacks a column a rule reads is an error and never an empty value; the retention rule compares a missing cell as empty today, so a column read by its old name would compare equal and pass. The map is a history reading like the old-shape branches: the current registry and a current Task carry the new names only.
- **Recorded rows (W03-D01).** The move changes no row. A Task whose base is in the old form and whose proposed text is in the form passes the retention and work-row rules because both sides hold the same rows under different headings; the same move with one changed, removed or reordered evidence cell fails. That pair of cases is the recorded form-only route of W03-D01, and it is a property of the two-registry read, not an exemption. For every moved Task the Task records that each data row of each of its tables is byte-identical and in the same order, with a hash of the data rows of each table before and after; the header line of the evidence table is the one line of a recorded table that changes.
- **Transitional adapter (line 39).** Line 39 of the W03 prompt asks for the consumer list and the end condition of a temporary adapter. The header map is one constant in `scripts/document_contracts.py`, beside the typed `task_execution` binding: `Evidence` to `Evidence ID`, `Check` to `Command` and `Criteria` to `Consumer`. One function applies it, to the rows of a side whose registry binds the old names. Its consumers are the evidence reader `task_base_evidence_rows` in `scripts/validate-links-and-owners.py` and, through the rows it returns, the six call sites and `_evidence_context` in `scripts/validate-document-lifecycle.py` and the retention, evidence and `TASK-ITEM-` rules of `scripts/document_lifecycle.py`. No rule holds a second copy, and no current registry or current document is read through it. Only a registry of a MAJOR below the one this package sets binds the old names, so the map and its function are removed, with their tests, when `READABLE_REGISTRY_MAJORS` no longer holds such a MAJOR; the package that drops the last one from the tuple removes them and records it.
- **Work residue ledger validator.** `_task_doc` in `scripts/validate-work-residue-ledger.py` (lines 142 to 146 at `a8c689e5`) calls `task_base_evidence_rows` without a registry, reads the columns `Evidence` and `Result` by literal name and turns a missing table into an empty mapping, so after the move it would find no evidence row and report nothing. It already loads the registry for its `work_residue` block, so it passes the `task_execution` binding of `sdlc/task` from that same registry to the reader and reads the evidence identity as `Evidence ID` and the result as `Result`, the names the binding lists. A Task whose evidence table or either column is missing is an error and never an empty mapping. It reads the current tree only, so it is no consumer of the header map. `tests/test_work_residue_ledger.py` takes the new header and the new host section.
- **Tables (W03-D08, W03-D65).** Lines 307 and 739 of the W03 prompt name the Task table as evidence id, input, command, result and consumer, and that role table exists in every Task with nine columns: `Evidence`, `Criteria`, `Work Unit`, `Check`, `Input`, `Result`, `Location`, `Required`, `Resolves`. The table takes the common names by a header map that changes no row (lines 759 and 684); this supersedes the unchanged names of W03-D61. The map is by meaning. `Evidence` becomes `Evidence ID`. `Input` stays `Input`. `Check`, the named check or command that was run, becomes `Command`. `Result` stays `Result`. `Criteria`, the Spec criteria whose acceptance uses the row, becomes `Consumer`, because the consumer of a piece of evidence is the criterion decision it supports. `Location` does not become `Consumer`: it says where the evidence can be read again and not who uses it, and the Task example of the v14.7 package keeps the location as a column of its own beside the criterion. This partition differs from the one first proposed when W03-D65 was relayed for drafting, which put `Criteria` in the extension and left `Consumer` to be mapped by meaning: that leaves `Consumer` without a source column, so either `Location` would take a meaning it does not have or every recorded row would gain a cell, and line 684 keeps recorded values unchanged. The W03 coordinator accepted the difference on 2026-11-14 as an implementation choice within W03-D65; it is no separate user decision. `Work Unit`, `Location`, `Required` and `Resolves` have no common name and the evidence rules read them, so they keep their names as the registered column extension. The columns keep their recorded order, `Evidence ID`, `Consumer`, `Work Unit`, `Command`, `Input`, `Result`, `Location`, `Required`, `Resolves`, because reordering would rewrite every recorded row; the common contract names the shared columns and not their order. No column is dropped and no cell is added. The TemplateDefinition records `Results` in `task-verification-evidence-results` with these nine keys, `Criterion Decisions` in `task-acceptance-decision-criterion-decisions` with the five acceptance keys, and `Lifecycle Traceability` in `task-lifecycle-traceability` with the seven body-contract columns; the last two are not the role table and keep their names.
- **Residue table (W03-D61).** SPEC-0191 puts a Task's live `Residue Handoff` table under the H3 of that name in the evidence section, after the evidence table, and registers its host in `work_residue` so that this package moves it by a registry edit. `Residue Handoff` is the second registered conditional local H3, under Verification Evidence, and only the host section in `work_residue.task_table` changes, from `Task Evidence` to `Verification Evidence`. The table stays where it is, after the evidence table, its rows do not change and the ledger's host and heading reading does not change. It is not moved under Handoff and not demoted to an H4.
- **Approval and safety block (W03-D61).** The Task's eight labelled fields under `Approval and Safety Boundaries` state allowed and forbidden paths, required approvals, validation, secret handling, rollback and evidence location; `scripts/validation/repository/quality.py` requires that heading and the eight labels in the template, and the work lifecycle names the section. The block moves whole under Scope > Inputs and Authority, whose content is the input revision, allowed files, decisions and authority; the quality check requires the eight labels under that form section instead of the old H2; and the policies name the form H3. This follows what W03-D52 decided for the Plan's `Global Constraints`. No local H3 is registered for the block.
- **Heading map, applied to every Task.** The old H2 headings are removed and their bodies move under the form H3 named here in their old order; a paragraph is never split and no table is edited.
  - Scope > Objective and Parent: the `Overview` body. Scope > Inputs and Authority: the `Inputs` body, then the `Approval and Safety Boundaries` block, whole and unchanged (W03-D61).
  - Execution Log > Work Performed and Execution Log > Blockers and Decisions: one pointer or explained-none line each, because a Task records its work in the rows below; then `Lifecycle Traceability` as the local H3 with the `Task Table` table unchanged.
  - Verification Evidence > Results: the evidence table of `Task Evidence`, with every H3 that follows it in that section as an H4 in place, apart from `Residue Handoff`, which stays an H3 as the registered local extension. Verification Evidence > Resolution Links: one pointer line to the `Resolves` column. After the move the H3 of this section stand in the order Results, Resolution Links, `Residue Handoff`: `Residue Handoff` is the last H3 of the section today and stays last, so the pointer H3 Resolution Links is placed after the Results content and before it.
  - Acceptance Decision > Criterion Decisions: the `Criterion Acceptance` table. Acceptance Decision > Remaining Conditions: one pointer or explained-none line.
  - Handoff > Promotion Receipt: one pointer or explained-none line. Handoff > Next Owner: the `Verification Summary` body.
- **SPEC-0161 Task (W03-D50).** It moves by the same map. Of its 14 H3 under `Task Evidence` at `a8c689e5`, the 13 from `Edition Delta` to `W03 Decisions` become H4 under Results with the same anchors, and the fourteenth, `Residue Handoff`, which SPEC-0191 added, stays an H3 as the registered local extension of W03-D61; its `Lifecycle Traceability` stays H3; SPEC-0191 registers five of the 13 as `historical_tables`, each by its Task path and heading text (`Document Form Handoff`, `Stage QA Handoff`, `Conflicts`, `Stage Follow-up Handoffs` and `W03 Decisions`). If that gate cannot resolve a registered heading at level 4, the author stops and asks the user, because the ledger's script is in scope for its read of the evidence rows only. Its status stays `completed`.
- **Open Tasks.** The set of Tasks is read from `main` after the rebase: every file under a `tasks/` folder of `docs/03.specs/`. At `a8c689e5` it is the SPEC-0161 Task alone; at implementation it holds at least that Task and this package's own, and the Task of any other package still open. Each moves in the implementation commit and gains an appended evidence row with its before and after hashes and the reason. The Task records the inventory.
- **Content changes.** These are the only changes to what a Task says: the heading lines; the header line of the evidence table, by the map; the pointer and explained-none lines the map names, each real prose (`BODY-SECTION-BARE`); and a positional word a move makes false, corrected to name the heading. No row changes.

The Tasks in the tree are below 1.0.0, where the document authoring policy raises the minor for an incompatible change, so each moved Task takes one minor raise; a Task at 1.0.0 or above would take a major raise. The template keeps `version` `0.1.0`.
- **TemplateDefinition and record (W03-H13).** `common/template-sdlc-task` stores the eleven definition keys of SPEC-0196, with `contract_version` `COMMON-DOC-FORM-1/` followed by `common_forms.version`, and the 19-field record derived for it passes `REGISTRY_TEMPLATE_RECORD`. With it the last SDLC template has a definition.

### Failure and Edge Cases

Edge cases and error handling:

- SPEC-0189 and SPEC-0191 have merged. The remaining merge order is SPEC-0207, then SPEC-0192 to SPEC-0200, then this package. It depends on SPEC-0207 for the SemVer form of the Registry Schema Version, its bump rule, the constants `REGISTRY_MAJOR` and `READABLE_REGISTRY_MAJORS` and the tests derived from them; on SPEC-0200 for the Spec and Plan forms, the `#criteria` fragment and the registry-driven Plan reader; on SPEC-0196 for `contract_version` and `REGISTRY_TEMPLATE_RECORD`; on SPEC-0193 for `relationship_contract` and `LINK-FRAGMENT`; on SPEC-0191 for `work_residue`; and on SPEC-0192 for the generator, whose tests for a Task run against the new template. SPEC-0201 and the Policy package that follows it share only the registry and the SPEC-0161 Task with this package and are ordered by their own Plans.
- The write guard judges every structured write against the registry in the working tree and fails closed for a MAJOR it does not implement, so the MAJOR step moves the registry, the schema `const`, `REGISTRY_MAJOR`, `READABLE_REGISTRY_MAJORS` and `DOC_REGISTRY_MAJOR` in the order the Plan fixes and in one commit. A branch that was cut before this package holds all of them at the earlier MAJOR until it rebases.
- This package's own Task is written in the form that holds at its package commit and moves in its implementation commit; its review and approval rows are recorded rows and do not change.
- A registry from before the evidence binding existed keeps the literal `## Task Evidence`; package 7 may remove the H2-list model but must keep that branch for as long as old commits are replayed through `registry_at(commit)`.
- A Task that is `completed` or `cancelled` moves like any other; no rule freezes its headings, and its rows are compared like those of an open Task.
- The evidence reader takes the first table of the evidence H2, so no table may precede the evidence table under Verification Evidence; the pointer lines the map adds are prose.
- The counts and line numbers are those of `a8c689e5`; the Task records them again after the rebase.

Failure modes, fallback and human escalation:

If SPEC-0207 has not merged, if the write guard cannot be moved to the new MAJOR without a tree state that blocks every write, if a recorded row of any Task would differ after the move, if a `TASK-` rule cannot be shown active on the form before the registry binds it, if a rule cannot read a recorded evidence row through the header map, if a Task holds text that no row of the heading map places, or if the ledger reader of SPEC-0191 cannot follow the host by the registry edit that W03-D61 decides, the author stops and asks the user. If any document outside the named scope gains a diagnostic, the change is wrong and is fixed before commit.
