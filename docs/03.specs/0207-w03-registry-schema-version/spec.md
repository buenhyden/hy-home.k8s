# W03 Registry Schema Version Mapping Technical Specification (Spec)

## Overview

This approved change contract is the Registry Schema Version package of the W03 stage of the external v14.7 execution package. It applies the fourth resolution of W03-D65, which the user decided on 2026-11-14 ("`W03 프롬프트에 작성된대로`", meaning that the W03 requirement text governs a conflict with a current rule) and which SPEC-0193 records in the [SPEC-0161 Task](../0161-w00-v14-7-delta-intake/tasks/tsk-0001-w00-v14-7-delta-intake.md). REQ:862 says the Registry serialization version is separate from the profile content version and that "an existing value in integer form moves by an explicit mapping after the consumers are analysed". REQ:890 says that `v14.5`, `v14.6` and the integer `schema_version` are never converted wholesale to `1.0.0`; the real past facts and naming system are investigated, a meaning-preserving mapping is made, and the current valid version is chosen. REQ:877 to REQ:882 define the bump rule (MAJOR, MINOR, PATCH and NO_CHANGE). Today `docs/99.templates/registry.json` holds the integer `10`, SPEC-0190 named it a Registry Schema Version and left it an integer (frozen text at `058e71ae:docs/03.specs/0190-w03-semver-vocabulary/spec.md`), ADR-0059 Decision 1 says it "stays 10", and W03-D63 of SPEC-0205 planned to raise it to the integer 11. An integer cannot carry the MINOR and PATCH steps that REQ:878 and REQ:879 require, so under W03-D65 this package replaces the integer by a SemVer value through an explicit mapping, chooses the current value, and states the bump rule, before any later package changes the version. The [Task](tasks/tsk-0001-w03-registry-schema-version.md) records execution and the [Plan](plan.md) orders the work.

### Decisions (W03-D66)

On 2026-11-14 the user decided the six questions of the first draft as W03-D66; the package commit appends the W03-D66 row to the SPEC-0161 Task. Open question: none.

1. **Representation.** A SemVer string (REQ:862 and the glossary term of SPEC-0190). This supersedes the integer-11 bump of W03-D63, which W03-D65 already sent to this package.
2. **Current version.** The declared generation 10 maps to `10.0.0` (REQ:890, preserving the declared fact). This package's own change, integer to string, breaks every reader that was valid before, so it is MAJOR (REQ:877) and the registry lands at `11.0.0`.
3. **Additive optional key.** MINOR only when every consumer that reads a registry of another revision tolerates it, otherwise MAJOR (REQ:878). Applied to the repository: the strict loader (`validate_registry_authority` with `OPTIONAL_TOP_LEVEL_KEYS` in `scripts/document_authority.py`) and the profile schema (`additionalProperties: false`) reject an unknown key, so a new top-level key is MAJOR.
4. **Scope.** The Stage 99 registry only. The other integer versions are recorded as surveyed and handed to their owners, with no bulk conversion (REQ:890): `.agents/roles/registry.json` (2) and the two bindings files (1) to W01; `scripts/validation/registry.json` (`schemaVersion` 4) to W05; the work residue ledger (1) to the owner of SPEC-0191; the workspace memory database (1) to its W08 owner.
5. **ADR.** This package carries its own amending ADR, ADR-0061 in the ADR form of its day (W03-D69); SPEC-0198's ADR moves to ADR-0062.
6. **Landing position.** Right after SPEC-0191 and before SPEC-0192 and every later package (REQ:875, declare the public contract first).

- **Mapping (REQ:890).** An integer generation `N` of 1 to 10 maps to the SemVer value `N.0.0`, because each generation was a pinned reading of the registry and the integer scheme recorded no compatible revision, so MINOR and PATCH are 0. The mapping names a generation; it makes no compatibility claim between generations, which the table above does not establish for generations 1 to 5. It is order preserving and meaning preserving, it yields `1.0.0` only for generation 1, and it resets no number (REQ:143). A blanket conversion of every value to `1.0.0` was not chosen because it erases the generation order that code and history rely on.
- **Current version (W03-D66).** The declared generation 10 is `10.0.0`; the four optional sections above and `work_residue` of SPEC-0191, which lands first, are part of generation 10 and carry no separate step (the integer scheme had no level for them; under the rule below each would have been MAJOR). This package replaces the integer by a string, which breaks every reader that was valid before, so it is MAJOR and the registry lands at `11.0.0`.
- **Later registry changes (W03-D66).** The bump rule binds each registry change that lands after this package at its implementation commit: that commit applies the bump and its Task records the level and the reason as evidence. A new top-level key or any other MAJOR step also edits the allow list `OPTIONAL_TOP_LEVEL_KEYS`, the schema and the version constant and pins named below, so that commit checks its own Spec scope against those files and stops for the user when the scope does not cover them. This package edits no later Spec; the approved packages that land after it (SPEC-0192, SPEC-0195, SPEC-0197 and SPEC-0198) are checked that way at their commits, and the Specs under revision (SPEC-0193, SPEC-0196 and, by its own drafter, SPEC-0205) name their expected level and paths.
- **Serialization.** `schema_version` is a JSON string holding a SemVer value of `scripts/semver_grammar.py` with no prerelease and no build metadata, in the registry and as the `const` of the schema property. A reader that needs the number of the MAJOR level reads it from the string. An integer value at the current path is refused with a message that names the mapping.
- **One reader function and one constant.** `registry_schema_version(raw)` in `scripts/document_contracts.py` returns the SemVer string for a registry mapping: a string that meets the grammar is returned as is, and an integer 1 to 10 returns `N.0.0` (the mapping, in the one place that needs it, for registries read from history); anything else raises, so a boolean, 0, a number above 10 and a malformed string fail. `scripts/document_authority.py` owns two constants: `REGISTRY_MAJOR` (the MAJOR number the code implements, 11) and `READABLE_REGISTRY_MAJORS` (an explicit tuple of the MAJOR numbers the history reader reads with their own typed reading, `(10, 11)`). The loader, the strict schema check and `registry_at` read them; none holds its own copy. The write guard must run from the checkout with the standard library only, so it keeps one module-level constant `DOC_REGISTRY_MAJOR` in `scripts/provider_write_guard.py` (the pin that `load_document_routes` reads today as the literal 10) beside a stdlib copy of the grammar; a consistency test compares that constant with `REGISTRY_MAJOR`, and a corpus test compares the stdlib grammar with `scripts/semver_grammar.py`. A MAJOR bump therefore edits `REGISTRY_MAJOR`, appends the new number to `READABLE_REGISTRY_MAJORS` and edits the guard copy, with the registry value and the schema `const`.
- **Compatibility rule for readers.** The loader and the write guard accept the MAJOR number they implement and refuse any other. The history reader `registry_at` reads every blob whose MAJOR number is in `READABLE_REGISTRY_MAJORS` with its own typed reading (`_typed_registry_from_mapping`), so a history blob with the integer 10 yields its own profiles as it does today, and falls back to the current registry only for a blob it cannot read (generation 9 and earlier, a `schemaVersion` spelling, a malformed value). A later MAJOR step appends its new number to the tuple and drops an old number only when the replay window no longer reaches a blob of that MAJOR number. The strict schema pins the exact current value. Within one MAJOR number MINOR and PATCH steps change the registry and the schema `const` only.
- **Bump rule (REQ:877 to REQ:882).** The public contract of a Registry Schema Version is what code reading the registry observes: the top-level keys, the profile and nested keys with their types and requiredness, the enumerations and states, the meaning of a value and the diagnostics a reader derives from it. The release unit is one change set that lands on `main`; several changes in it take the highest level, a MAJOR step sets MINOR and PATCH to 0, and a MINOR step sets PATCH to 0. The commit type does not decide the level.
  - MAJOR: a change that breaks a registry or a consumer that was valid before: a required key added, removed or renamed, any key added where a strict consumer rejects an unknown key, a state or profile family removed, a changed meaning, a stricter obligation, a changed output structure. Fixing every consumer in the same pull request does not lower the level. Examples: removing the required `sections` key (SPEC-0205); a new top-level section such as `relationship_contract` (SPEC-0193), which the strict loader and the schema reject until their allow lists change.
  - MINOR: a compatible addition that earlier valid producers and consumers survive and no strict consumer rejects (W03-D66, REQ:878). No such location exists in the registry today, because the schema closes every object; the level stays defined for the first location that is opened. A real deprecation of a key is at least MINOR.
  - PATCH: a compatible fix that enforces an already declared contract or a wording change of the schema that changes no accepted input. A check that newly refuses an input the old version accepted is not a PATCH, whatever the change is called.
  - NO_CHANGE: a change that leaves the serialization shape of the registry untouched, such as profile content, a template, a path pattern, a section list edit, a form, an extension, a TemplateDefinition entry, a body-contract column list or a description sentence of the schema, or a change of another object (a Document Revision or a Contract Version). The value stays.
  - Each registry change records its level and the reason in its Task. A version that has landed is never reused, lowered or rewritten.
- **Transitional adapter (REQ:37).** The integer branch of `registry_schema_version` exists for one consumer, the history reader `registry_at`, which reads registry blobs of earlier commits that still hold the integer. It ends when the cumulative-history rules can no longer read a commit that predates this package (after the Q-07 baseline or when the bounded history window has passed it); the Task records that end condition. No other consumer accepts an integer, and no mapping table stays in a current document (REQ:890 treats the transition material as temporary input); the table above leaves with this package and Git recovers it.

## Interfaces & Data Structures

- `docs/99.templates/registry.json`: `"schema_version": "11.0.0"`; `docs/99.templates/contracts/document-profile.schema.json`: the property is a string with `const` `"11.0.0"`.
- `scripts/document_contracts.py`: `registry_schema_version(raw: Mapping[str, Any]) -> str`, raising `DocumentContractError` with rule `REGISTRY_SCHEMA` for a value outside the contract; the `Registry` dataclass field `schema_version` becomes `str`; `load` and the strict check call the function; the strict check compares the MAJOR number with the one it implements.
- `scripts/validate-document-lifecycle.py`: `registry_at` calls the function for a history blob, reads it with its own typed reading when its MAJOR number is in `READABLE_REGISTRY_MAJORS`, and keeps the fallback to the current registry only for a blob it cannot read.
- `scripts/provider_write_guard.py`: `load_document_routes` accepts a string whose MAJOR number equals `DOC_REGISTRY_MAJOR` (11) and refuses an integer, a malformed string and another MAJOR number, failing closed as today (`HOOK-DOC-REGISTRY`).
- Tests: the new `tests/test_registry_schema_version.py` fails first and then passes for: the string and the schema `const`; an integer, `"10"`, `"v10.0.0"`, `"10.0"` and `"10.0.0-rc.1"` refused; the mapping of each integer 1 to 10 to `N.0.0` and a refusal of a boolean, 0 and 11; `registry_at` reading a history blob with the integer 10 as `10.0.0` and returning that blob's own profiles, not the current ones, and falling back only for generation 9, a `schemaVersion` spelling and a malformed value; a corpus test of the guard's stdlib grammar against `scripts/semver_grammar.py` for a prerelease, build metadata, `011.0.0`, `"11"`, `"11.0"`, booleans and `None`; the guard accepting the current value and a MINOR step of it and refusing the integer 10, the previous MAJOR value and the next MAJOR value, all derived from `REGISTRY_MAJOR`; the guard constant `DOC_REGISTRY_MAJOR`, `REGISTRY_MAJOR`, the schema `const` and the registry sharing one MAJOR number; and generation 10 not mapping to `1.0.0`. The version-pinning tests are converted so that none holds a version literal: `tests/test_registry_schema_version.py` (new), `tests/test_k8s_pre_edit_hook.py` (the synthetic registries at the current and the refused value), `tests/test_common_form_tree.py` (the repository registry assertion at line 1217) and `tests/test_document_lifecycle_cumulative_history.py` (the `registry_at` mock). Each derives its values from `REGISTRY_MAJOR` and `READABLE_REGISTRY_MAJORS` (a current value, the next MAJOR number as a refused value, and every readable MAJOR number), so a later MAJOR step edits the constants and no test.

## Edge Cases & Error Handling

- A history blob that still uses the `schemaVersion` spelling (generations 1 to 8) is not read by `registry_at`, which reads `schema_version` only, so it falls back to the current registry as today; no mapping is applied to it.
- A MINOR or PATCH step lands without a change to the guard, `registry_at` or the loader, because they check the MAJOR number only; the schema `const` and the registry change together. A MAJOR step also edits `REGISTRY_MAJOR`, `READABLE_REGISTRY_MAJORS`, the guard constant and, for a new key, `OPTIONAL_TOP_LEVEL_KEYS` and the schema.
- The cumulative-history rules read blobs from earlier commits (REQ:113, REQ:778). A review measured the replay window: all 256 commits carry integer-10 blobs and 237 of them differ from the current registry, so a fallback would change their classification. After this package a blob with the integer 10 maps to `10.0.0`, is in `READABLE_REGISTRY_MAJORS`, and is read as itself; the replay result over the window is measured before and after and must be equal.
- Q-07 renumbering never resets this value (REQ:143).
- SPEC-0191 merges before this package and this package before SPEC-0192 and every later package; each later package rebases on `main`, renumbers appended rows and applies its own bump at its implementation commit. The SPEC-0205 Spec and Plan are revised by their drafter to the string form and a MAJOR step before they are approved again.

## Failure Modes & Fallback / Human Escalation

If ADR-0061 is not accepted by the user, the package does not complete and SPEC-0198 does not start, because its retained form applies to accepted ADRs only and ADR-0061 is written in the old form; the author stops and asks the user. If a consumer that reads `schema_version` is found outside the list in this Spec, the author stops and adds it to the Task before editing it. If a strict document validator gains or loses a diagnostic, or the pre-edit hook accepts a registry that the strict check refuses, the change is wrong and is fixed before commit. After two failed attempts with no new information the author stops and reports a repository defect.
