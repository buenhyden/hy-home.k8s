# W03 SemVer Version Tests Technical Specification (Spec)

## Overview

This approved change contract closes the test half of the SemVer section of the v14.7 2026-11-13 revision of the W03 task (`SEMVER-POLICY.md` sections 1, 4 and 5; task file lines 854 to 899). SPEC-0190 (merged by pull request #251 at `cd174848`; frozen source `058e71ae:docs/03.specs/0190-w03-semver-vocabulary/spec.md`) gave the repository one SemVer 2.0.0 grammar, eight glossary terms and a version paragraph in `document-authoring.md`. It left two things out by design: it excluded "a version comparison for documents, which no current consumer needs", and it named W05 as the owner of any further SemVer regression "when a new consumer compares versions". The revision asks for a survey of every version-bearing object (section 1) and for tests of ten situations (section 5): a valid and an invalid form, prerelease order, build metadata precedence, tampering with a released version, the four combinations of old and new producer and consumer, a missing version, an unchanged version, a downgrade, and the separation of Q-07 numbering from versions. SPEC-0190 already covers the first four through its case tests. This package adds the other six on the surfaces named below, and wires each new guarantee into a check that already runs, as the task file requires.

The survey found that a version is compared by exactly one consumer today: `scripts/release.py` refuses a tag that does not exceed every earlier tag (`RELEASE-VERSION-NOT-INCREASING`) and a changed released changelog section (`RELEASE-CHANGELOG-HISTORY-DRIFT`). No document, registry or contract version is compared, so a downgrade of a document `version`, a rewritten `shared_contract` edition or a lowered `schema_version` passes every check. Three readers pin the registry `schema_version` by equality at `81096a83` (`scripts/document_contracts.py`, `scripts/provider_write_guard.py`, `scripts/validate-document-lifecycle.py`); SPEC-0207 (draft, landing right after SPEC-0191) turns that value into the SemVer string `11.0.0` with readers that check the MAJOR number only, which makes them the only real old-consumer and new-consumer pairs in the tree and the natural subject of the producer and consumer matrix. The [Plan](plan.md) orders the work and the [Task](tasks/tsk-0001-w03-semver-tests.md) records execution.

## Strategic Boundaries & Non-goals

- In scope (writer W03 for the contract surfaces, with W05 for validators and tests; each W05 file is edited under the same-change rule of `docs/99.templates/AGENTS.md` rule 1 and is recorded as a delegation by the closing records package, SPEC-0209): the survey of version-bearing objects (the nine columns of the task file, kept in the Task); a `precedence` function in `scripts/semver_grammar.py` that `scripts/release.py` imports in place of its private `_precedence`; a base-to-proposed version comparison for the surfaces in the Contracts section, added to the comparison that `scripts/validate-document-lifecycle.py` and `scripts/document_lifecycle.py` already run; tests for the six situations; one added sentence in the version paragraph of `.agents/governance/document-authoring.md`; the check cell of REQ-0003 FR-0027 (with that document's frontmatter `version` and `updated`); `scripts/run-contract-tests.py` and `scripts/validation/registry.json` rows for the new test module (the validation registry, not the Stage 99 registry); each edited document's frontmatter `version` and `updated`; this package, the Stage 03 README entry and reviewed `.secrets.baseline` entries.
- Not in this package: any change of an existing version value; the choice of a MAJOR, MINOR or PATCH level for a change (the policy does not automate the exact value choice, so no check demands a bump when a body changes); the release producer, tags, `CHANGELOG.md` and GitHub Release (W06; `scripts/release.py` keeps its behavior apart from the shared precedence import); any change of the grammar or of the SPEC-0190 case tests; the representation, mapping, value and bump rule of the registry `schema_version` (SPEC-0207 owns them under W03-D65) and its raise (SPEC-0205); artifact identities and Q-07 numbering (W03-D30), except the one separation case below; input package edition labels such as `v14.7`, which are not SemVer; the adoption record of COMMON-DOC-FORM-1, which SPEC-0209 owns; the released-edition rule never extends to `common_forms` (see the scope of the comparison).
- No push, PR or merge without the user's approval. Open question: none. This Spec stays `draft` until its approval receipt exists.

### Decisions (W03-D68)

On 2026-11-14 the user adopted the recommended option of each of the four questions this package raised; the decision row W03-D68 is appended to the SPEC-0161 Task with the package commit. Open question: none.

- **Document comparison scope.** Contract and registry versions, plus a downgrade check on every document `version`. A missing document `version` stays a profile error. No check demands a higher version when a body changes, because the policy leaves the level to the actual compatibility difference.
- **Where it runs.** In the base-to-proposed comparison of the lifecycle validator, with one sentence in the `document-authoring.md` version paragraph (a W01 file) and an amended FR-0027 check cell saying that the comparison judges version fields only and no state edge. `document-lifecycle.md` (W04) is left untouched; W04 is consulted because the lifecycle validator is its interface.
- **Survey table.** It lives in the Task only; the durable protection is the tests and the registry bindings.
- **Old producer and consumer.** Edition fixtures: the old producer is a registry or document written under the previous edition, the new producer one written under the current edition, the new consumer is the current code, and the old consumer is the same code run with the previous MAJOR number that the `schema_version` readers of SPEC-0207 implement. No test reads Git history or an old checkout, and no old reader code is copied.

Settled by the task file and not asked: the integer `schema_version` leaves its integer form by an explicit mapping (task file line 862; W03-D65; SPEC-0207 applies it, and its final form is the SemVer string `11.0.0`), so this package tests that form.

- **Scope of the comparison.** The comparison reads the Stage 99 registry `schema_version`, `shared_contract.version`, `shared_contract.stage`, `shared_contract.content_digest`, `shared_contract.source_revision` and `common_forms.version`, and each governed document's frontmatter `version`. It does not compare the skill envelope `metadata.version`, `consumer_version`, a `stage` regression (a fall from `adopted` to `candidate`), the other integer registries, or `common_forms` content: `common_forms` has no stored scalar digest of its forms, and decision W03-D67 of SPEC-0209 keeps it at `candidate`, so a released-edition rule would never apply to it (residual risk below). Each of these is recorded as not compared in the Task survey.
- **Comparison rules.** For a base and a proposed value of one object, the lifecycle comparison reports `LIFECYCLE-VERSION-DOWNGRADE` for a proposed value of lower precedence than the base, and `LIFECYCLE-VERSION-EDITION-CHANGED` when the base `shared_contract.stage` is `approved` or `adopted` and the same `contract_id` and `version` carry a different `content_digest`, `source_revision` or `source`. A proposed value equal in precedence but different in build metadata only is accepted, because build metadata never changes precedence. An equal value with equal content is accepted and demands no bump (an unchanged version). A `candidate` edition may change under an unchanged version. A document new on the proposed side has no base. The registry side reads scalar fields only from the raw JSON of the base blob (through the existing `_registry_blob`), and never builds a typed or parsed historical registry from it, as the comparison base rule at `scripts/validate-document-lifecycle.py` line 2538 requires. A missing version is not a new comparison rule: each surface already refuses it (see the mapping below).
- **Precedence.** `scripts/semver_grammar.py` gains `precedence(value)` for a bare SemVer string (the grammar refuses a `v` prefix, so a tag label is passed without it), returning the tuple that `scripts/release.py` builds today (major, minor, patch, release flag, prerelease parts) with build metadata ignored. `scripts/release.py` keeps `_precedence(version: SemVer)` as a thin wrapper that returns `precedence(version.label)`, where `label` is the tag without its `v`; `parse_version` is unchanged, so `tests/test_semver_grammar.py::test_precedence_follows_semver_not_text_order`, which calls `release._precedence(release.parse_version("v" + value))`, and the other SPEC-0190 tests stay unchanged and green. No text, float or three-number comparison is used. No semver library is installed in the pinned environment (`packaging` follows PEP 440, not SemVer), and the policy forbids installing a new tool, so the repository grammar and this function are the reused parser.
- **Producer and consumer matrix.** For each increment class in the case file (`SEMVER-CASES.json` of the v14.7 revision: a renamed required heading is MAJOR, an optional feature that valid inputs still satisfy is MINOR, a correct refusal of an already invalid input is PATCH, an unchanged object is NO_CHANGE) the test runs the four combinations of old or new producer against old or new consumer on the `schema_version` readers (a registry of the MAJOR number the reader implements loads whatever its MINOR and PATCH numbers, and another MAJOR number is refused or falls back, as SPEC-0207 defines). A MAJOR change must be refused by the crossed pairs and accepted by the matching pairs, a MINOR or PATCH change accepted by every pair the earlier edition accepted, and NO_CHANGE accepted by all four. The task file (line 878) adds that an added key which a strict parser rejects is not automatically MINOR: one row adds an unknown optional top-level key to a registry and feeds it to the strict registry schema, which refuses it, so the expected class is MAJOR and the row fails if it is classed MINOR. **Documents.** No earlier consumer compares document versions. The two old-consumer combinations for DOC-REV therefore run the consumers that existed before: the frontmatter schema pattern and the strict profile check, which SPEC-0190's cases cover, and they must accept an unchanged and a risen version and refuse a malformed one. The old-producer and new-consumer row is a fixture: a base document written before this package and a proposed one, fed to the comparison. The new-producer and new-consumer combination is the paired accept and refuse cases. The run of the comparison over every current document against its parent commit is Task evidence, recorded once and not a test, because a test never runs a gate over the repository (`tests/test_validation_tooling_ownership.py`). The matrix is a table in the test module whose rows are copied from the case file, as SPEC-0190 copied its cases; nothing is read from `_workspace/`.
- **Numbering separation (task file line 864).** Three cases. A base and proposed pair at the same path whose artifact identity is renumbered but whose `version` is unchanged is accepted; the comparison reads the `version` only. A same-path pair whose artifact identity restarts at a low number and whose `version` resets from a higher value to `0.1.0` is refused as `LIFECYCLE-VERSION-DOWNGRADE`, because a renumber never resets a version. A package edition label such as `v14.7` is never passed to the SemVer grammar. Limit: the comparison pairs a base and a proposed document by path, so a renumber that moves the file to a new path is not paired and its version reset is not seen here; the carry-over of versions across such a move belongs to the separate Q07 final cutover task of the v14.7 package, which this package does not execute.
- **Existing coverage is mapped, not repeated.** The Task maps each required situation to its surface, the check that decides it and the test that proves it. `RELEASE-VERSION-NOT-INCREASING`, `RELEASE-CHANGELOG-HISTORY-DRIFT`, `RELEASE-INITIAL-ALREADY-USED` and `RELEASE-VERSION-INVALID` belong to the TAG object, and a situation with no test gets one in `tests/test_release.py` or the new module. SPEC-0190's case tests keep the valid, invalid, prerelease and build-metadata situations. A missing version is refused today by the strict Markdown profile check for a document, by the registry schema for a contract version, by the SPEC-0207 reader function for `schema_version` and by `RELEASE-VERSION-INVALID` for a tag; these cases and the `schema_version` reader rows of the matrix are mapped to those checks and are regression cases that already pass, not failing-first.
- **Failing-first per case (task file line 898).** A refusal case (downgrade, same-path version reset, changed released `shared_contract` edition) is run first on a scratch copy before the comparison exists and fails because the diagnostic is absent, then passes. An accept case (unchanged version, a rise, build-metadata-only difference, a candidate edition that changes) fails first only through its absent entry point, an import or lookup error, and is always paired with a refusal case so that a comparison that accepts everything is caught. The strict-parser MAJOR row and the document-comparison rows are failing-first the same way; the reader rows and the missing-version rows are not, and the Task says so for each.
- **Policy sentence.** The version paragraph of `.agents/governance/document-authoring.md` gains one sentence: a check refuses a lower version and a changed released edition, accepts an unchanged version without demanding a bump, and never chooses the level of an increase.
- **Requirement check cell.** The check cell of REQ-0003 FR-0027 (`docs/01.requirements/0003-workspace-agent-governance-platform.md`, whose cell reads "Lifecycle check judges state edges only.") is amended, as SPEC-0191 amended the cells of FR-0019 and FR-0022, to say that the lifecycle check judges state edges and, for version fields only, a lower or changed-released value, and chooses no level. The requirement sentence is not changed. `.agents/governance/document-lifecycle.md` is owned by W04 and is left untouched; W04 is consulted because the lifecycle validator is its interface.

- **Own bump level.** This package edits no key, value or shape of the Stage 99 registry, so its level for the Registry Schema Version is NO_CHANGE: `schema_version` stays at the value SPEC-0207 and SPEC-0205 leave. Its `document-authoring.md` edit changes one sentence of a document and raises that document's Document Revision by the level its own diff shows, which the Task records.

## Core Design

[AD-0006](../../02.architecture/descriptions/0006-workspace-agent-governance-platform.md) owns the governance view; no component changes. The comparison is a function of two parsed values and an optional digest, called from the lifecycle comparison that already holds a base and a proposed side, so no new gate, script or registered validator is added. The cumulative-history replay of the lifecycle validator is not given the new rules (see Failure Modes).

## Data Modeling & Storage Strategy

No data changes. The survey is Task evidence and leaves with the package; its frozen commit and path recover it.

## Interfaces & Data Structures

`scripts/semver_grammar.py`: the existing `SEMVER_PATTERN` and `is_semver`, plus `precedence(value: str) -> tuple`. The lifecycle comparison gains the diagnostics above and no new CLI option. SPEC-0207's `tests/test_registry_schema_version.py` keeps the reader tests; this package adds no second copy of them. The new test module is `tests/test_semver_versions.py` in the `document` suite, with exact routes in `scripts/validation/registry.json`.

## Edge Cases & Error Handling

- A document new on the proposed side has no base and passes. A document deleted on the proposed side is not compared.
- A base `version` that fails the grammar (none today) is reported as the grammar error of the existing check and is not compared.
- A prerelease may rise to its release (`1.0.0-rc.2` to `1.0.0`) and may not fall back.
- Equal precedence with different build metadata passes and is recorded as unchanged precedence.
- A `candidate` edition that changes content under an unchanged version passes; the same change under an `approved` or `adopted` `shared_contract` stage is refused. The rule is tested on `shared_contract`, whose stage is `adopted`, and on a fixture; it does not apply to `common_forms` (see the scope of the comparison).
- A registry `schema_version` compares by `precedence` on the SemVer string; a base blob that still holds the integer reads as `N.0.0` through the reader function of SPEC-0207, and a value that function refuses is reported as its error and not compared.

## Failure Modes & Fallback / Human Escalation

If a current document, registry value or earlier commit fails a new rule, the author stops and asks the user rather than editing the value. If the new rules produce a diagnostic on the cumulative-history replay of the lifecycle validator, they are removed from the replay and kept on the base-to-proposed comparison, and the Task records the first commit that failed. If a strict document validator gains a diagnostic over the tree, the change is fixed before commit. Rollback is the revert of the implementation commit; the shared `precedence` function leaves with it and `scripts/release.py` regains its private copy.

## Verification Commands

- Record the four strict document validators before and after; diagnostics must be equal.
- `python3 scripts/run-contract-tests.py --root . --suite document`, `--suite document-lifecycle`, `--suite release` and `--suite validation-routing`; `python3 scripts/validate-affected-surfaces.py --root .`.
- A failing-first run of each new case on a scratch copy before the code exists, then the passing run.
- `ruff check scripts tests`, `ruff format --check scripts tests`; `python3 scripts/qa.py staged` and the commit hooks on the exact index.
