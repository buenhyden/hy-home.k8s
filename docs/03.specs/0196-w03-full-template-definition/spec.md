# W03 Full TemplateDefinition Record Technical Specification (Spec)

## Overview

This approved change contract is local-forms package 4 of the W03 stage of the external v14.7 execution package. It closes handoff W03-H15 and the rest of W03-H28 (decision W03-D26). SPEC-0186, SPEC-0188 and SPEC-0189 gave eight of the nine Stage 99 local roles of W03-D20 their forms and left `provider-native` without one (W03-D33); what remains of W03-H28 is the full TemplateDefinition record and the cleanup that SPEC-0189 names for this package. The package contract `TEMPLATE-DEFINITION-CONTRACT.md` and its schema `TEMPLATE-DEFINITION.schema.json` (SHA-256 beginning `e490cf40`) define one record of 19 required fields per template (R45-10). The registry stores ten of them in each `template_definition`, and its schema says that "role, version, headings and the rest are derived", but no function derives or validates the full record (W03-H15).

A read of `main` at `de64c58d` found 39 template profiles, 33 of them with a definition, each naming exactly one source profile whose frontmatter key lists equal the template's, and every listed key described in `frontmatter_keys`. A prototype derivation over those 33 definitions, run outside the repository against the package schema, failed in one way only: `headings` was empty for the nine templates whose role had no form at that commit. SPEC-0187 to SPEC-0189 remove one of the nine and give five a form, which leaves the three `provider-native` templates. On 2026-11-14 the user decided the five design choices of this package in W03-D56: the schema the record validates against, where `contract_version` lives, the record of a role without a form, the retirement of the heading-line path and the output of the record. The extension record for the empty `headings` of `provider-native` follows W03-D65, which the user decided on 2026-11-14 ("`W03 프롬프트에 작성된대로`") and which SPEC-0193 records: where the W03 requirement text (REQ) conflicts with a current rule, the REQ text governs, so REQ:290 (every TemplateDefinition states its headings) and REQ:37 (a product difference is allowed only as a conditional extension with condition, owner, verification, review and removal criteria) replace a silent tolerance. The decision is recorded in the [SPEC-0161 Task](../0161-w00-v14-7-delta-intake/tasks/tsk-0001-w00-v14-7-delta-intake.md) by this package's commit. This package merges after SPEC-0188 to SPEC-0195 and reuses the model of SPEC-0169 to SPEC-0195 (recovery in [REQ-0003 Archived Lineage](../../01.requirements/0003-workspace-agent-governance-platform.md#archived-lineage)). The [Task](tasks/tsk-0001-w03-full-template-definition.md) records execution and the [Plan](plan.md) orders the work.

## Contracts

- **Record.** `template_definition_record(raw_registry, profile_id)` returns, for a template profile that carries a definition, a mapping with exactly the 19 keys of the package schema in the order of its `required` list. It reads the registry mapping only, with no file, clock or Git state, so equal input gives equal output. It is the one place that joins profile, form and definition, and no derived field is stored a second time (REQ-0003-FR-0012).
- **Stored and derived.** Eleven fields are stored in the definition and eight are derived from registry data that already has one owner. One further optional stored key, `headings_extension`, exists only for a role without a form and feeds the derived `extensions` field; it is not one of the 19 fields.

| Field | Source in the registry | Kind |
| --- | --- | --- |
| `template_id` | The template profile's `id`. | derived |
| `contract_version` | `template_definition.contract_version`. | stored, new (W03-D56) |
| `role` | The template profile's `document_role`. | derived |
| `purpose`, `responsibility`, `non_goals` | The definition. | stored |
| `policy_refs`, `vocabulary_refs`, `applicability` | The definition. | stored |
| `metadata` | The source profile's `frontmatter` lists joined with `frontmatter_keys`. | derived |
| `headings` | The role's form in `common_forms`, without `link_only`. | derived |
| `tables` | The definition. | stored |
| `relationships` | `relationship_contract` (SPEC-0193). | derived |
| `lifecycle` | The source profile's entry in `lifecycle_domains`. | derived |
| `language` | `document_language` and the form's `language_rule`. | derived |
| `consumer_paths`, `validation`, `migration` | The definition. | stored |
| `extensions` | The form's `extensions`, and for a role without a form the definition's `headings_extension`. | derived |

- **Derivation rules.** Each rule reads one owner and invents no meaning.
  - `metadata` has one item per key that the source profile lists as required, optional or forbidden, in that order: `name` is the key, `meaning` its `purpose`, `data_type` its `data_type`, `writer` its `authoring_owner` (with `derived_from` when the key is derived) and `consumers` its `consumer_paths`. `requiredness` is `required` or `forbidden` by the list, and for an optional key it is `conditional` when the key entry has a condition and `optional` when it has none. `condition` is the key entry's condition, or a fixed English phrase per requiredness when the entry has none. A profile whose frontmatter mode is `absent` gives an empty list.
  - `headings` is the form's section tree with every package field (`section_id`, `level`, `parent_id`, `title`, `order`, `requiredness`, `condition`, `content`, `required_content`, `prohibited_content`, `empty_policy`, `validation_ids`, `children`) and without the local `link_only` flag. The form's `h1` is not a section and is not copied.
  - `relationships` has one sentence per entry of `relationship_contract.relations` that names the template profile or its source profile as a source or a target (its id, kind, `direction`, side and cardinality). After SPEC-0193 the kinds `authority` and `change-impact` are relations of their own (`policy-authority` and `consumer-impact`, sourced by every template profile with a definition), so no extra sentence is derived for them and the list is never empty for a template with a definition. A test asserts both sentences and that the sentence set equals the relations that name the profile.
  - `lifecycle` names the source profile's lifecycle family, its states in order and its initial states, or states that the source profile binds no lifecycle domain.
  - `language` names the language class the source profile answers to under `document_language`, read through `scripts/document_language.py`, followed by the form's `language_rule` when the role has a form.
  - `extensions` has one item per form extension: `condition` and `owner` as stored, `delta` naming the extension's `kind`, `id` and, where present, its title under its parent, `validation` its `verification`, and `expiry_or_review` its `review` and `removal` joined. For `headings_extension` the `delta` names the kind `empty_headings` and its `id`.
- **Schema (W03-D56).** The record validates against a tracked byte copy of the package schema at `docs/99.templates/contracts/template-definition.schema.json`, as the W03-H15 and W03-H28 rows ask ("a copy of the package schema"). A test pins its SHA-256, so a later edit is a deliberate change of both, and the Task records the package revision it came from. The existing `stage99-machine-contracts` route covers the file. A definition rewritten into `document-profile.schema.json` and field checks written in Python were not chosen, because either can drift from the package and gives W11 a weaker comparison base.
- **Contract version (W03-D56).** `contract_version` becomes the eleventh stored key of every `template_definition`, because it is the one field that no registry data determines for a local role. Its value is a contract identifier, a slash and a SemVer value of `scripts/semver_grammar.py` (the Contract Version of the Repository Vocabulary): `COMMON-DOC-FORM-1/` followed by `common_forms.version` for a COMMON-DOC-FORM-1 role, and `STAGE99-LOCAL-FORM-1/1.0.0` for a Stage 99 local role, `provider-native` included. Deriving one value for every template from `common_forms` was not chosen, because it labels the local roles of W03-D09 and W03-D20 as COMMON-DOC-FORM-1 roles; a machine marker on each form was not chosen, because it changes every form and still needs a rule for a role without a form.
- **Roles without a form (W03-D56, W03-D65).** The package schema requires at least one `headings` item (REQ:290), and W03-D33 keeps `provider-native` without a heading form. The three `provider-native` templates get a full record with empty `headings`. That difference from the common record is a conditional extension under REQ:37, stored in each of the three definitions as `headings_extension` with exactly five non-empty text fields and an `id`:
  - `id`: `provider-native-empty-headings`.
  - `condition`: the template's files are read by a native runtime (Claude Code agent and command files, Codex agent TOML) whose own format fixes their shape, so the repository imposes no heading tree on them (W03-D33).
  - `owner`: `platform`.
  - `verification`: `REGISTRY_TEMPLATE_EXTENSION`, which fails when the record is missing, incomplete, malformed or sits on a role that has a form, and the native projection checks of the agent-governance suite.
  - `review`: when a provider's native file format changes and whenever the `STAGE99-LOCAL-FORM-1` contract version changes.
  - `removal`: when `provider-native` receives a form in `common_forms` (a reversal of W03-D33) or the three templates leave the registry; the extension and its rule are then deleted.

  The registry check tolerates exactly one finding (`minItems` on `headings`), and only for a role that has no form in `common_forms` and whose definition carries a complete `headings_extension`; every other finding still fails, and a missing or incomplete record turns the tolerated finding into a failure. A definition on a role with a form that carries `headings_extension` fails too. Excluding the three templates was not chosen, because it leaves R45-10 unmet for real templates, a minimal form was not chosen, because it reverses W03-D33, and tolerating the finding without a record was not chosen, because REQ:37 allows a difference only as a recorded extension.
- **Registry check.** `REGISTRY_TEMPLATE_RECORD` runs in `current_registry_diagnostics`, so the strict registry validator reports it and the load path does not, because a comparison-base registry may lack the new key and `relationship_contract`. For every template profile with a definition it refuses: a derived record that fails the schema copy, naming the profile and the failing field; a `contract_version` outside the grammar above; a `COMMON-DOC-FORM-1` value that differs from `common_forms.version` or sits on a role without a form; two templates of one role with different values, and (`REGISTRY_TEMPLATE_EXTENSION`) a role without a form whose definition lacks `headings_extension` or whose record has a missing, empty or non-text field, a role with a form that carries one, a record with whitespace-only text in a field, a record with an extra or unknown key, a record whose `id` is not `provider-native-empty-headings`, an `owner` outside the registered owner set (the exact set is the `owner` values of the `common_forms` extensions together with `shared_contract.owner`, read from the registry when the rule runs and never hard-coded; at `81096a83` it is `platform` for all 49 extensions and `buenhyden` for the shared contract, and the provider-native profiles declare no owner constant), and a record on a profile whose `document_role` is not `provider-native` (the registered role set that the `removal` criterion names). `document-profile.schema.json` makes `contract_version` required and `headings_extension` optional in `template_definition`, and its description names the function instead of saying only that the rest is derived. `schema_version` is bumped by this package under the rule of SPEC-0207 (W03-D66), as the expected MAJOR step named in its Boundaries; `template_definition` itself and `frontmatter_keys` were added earlier without a change because the integer scheme had no level for them.
- **Heading-line cleanup (W03-D56).** SPEC-0179 let a role without a form name a table by its template heading line. Once SPEC-0189 lands, no real template does: the nine heading-line tables at `de64c58d` belong to the three reference templates, which move to section ids, and `provider-native` records no table. SPEC-0189 moves `LocalRoleTableTests` and `test_each_local_template_holds_its_recorded_heading_lines` to a synthetic profile and names this package for their retirement. The path is retired whole, in the order the work lifecycle sets for a one-use check. First the registry check gains its replacement, a table on a role without a form fails `REGISTRY_TABLE_SECTION`; then `BODY-TABLE-SECTION` with `_template_table_section_diagnostics` and its call, the form-less branch of the table check, `_TABLE_HEADING_LINE` and the `required_h2` parameter are removed; then the two synthetic tests and the constants only they use. Handing the path to phase-3 package 7 of W03-D49 was not chosen, because consumer-zero is reached here (REQ-0003-FR-0030), and retiring the tests alone was not chosen, because it leaves the code unprotected. SPEC-0188 names no cleanup for this package.
- **Output (W03-D56).** The function, the registry check and the tests are the whole delivery; no command prints the records and no generated file is tracked, because a tracked copy is a second owner that drifts and the comparison across repositories belongs to W11 (W03-H09, W03-H22), which can call the function.
- **Policy text.** `document-authoring.md` states which TemplateDefinition fields a definition stores and which the function derives, names the schema copy, and replaces the sentence about a template whose role has no form by one that says `provider-native` has no form, records no table and records its empty headings as a conditional extension with condition, owner, verification, review and removal. The Stage 99 README gains the same facts in its TemplateDefinition bullet and lists the new schema file; only that README text is Korean. The description of a table's `section` in `document-profile.schema.json` loses its heading-line half.
- **Residue and decisions.** The package commit appends the W03-D56 row to the SPEC-0161 Task with the user's exact words; no recorded row is edited. W03-H15 and W03-H28 close by the rules of the work residue ledger (SPEC-0191): after the user's acceptance their live `Residue Handoff` rows become terminal with the closing evidence row, and their ledger entries become terminal in the same commit and leave by the ledger's retirement rule.

## Core Design

[AD-0006](../../02.architecture/descriptions/0006-workspace-agent-governance-platform.md) owns the governance view; no component changes. The registry stays the single machine owner of document form and template definition ([ADR-0033](../../02.architecture/decisions/0033-common-document-contract-v9.md) as amended by [ADR-0059](../../02.architecture/decisions/0059-registry-common-form-model.md)); no ADR changes. The record is a projection: every derived field has one stored owner (the profile, the form, `frontmatter_keys`, `relationship_contract`, `lifecycle_domains` or `document_language`), so a change at that owner changes the record with no second edit. The package schema is the comparison base that the package contract names for the four repositories, which is why W03-D56 adopts its bytes and not a local rewrite.

## Data Modeling & Storage Strategy

Registry data: one new string per definition (33 definitions in the expected landed state; the count is read from the registry, never hard-coded) and one extension record in each of the three `provider-native` definitions. Contracts: one new schema file of about 10 KB and one changed definition in the profile schema. Code: one function, two registry rules, one replacement refusal, and the removal of one body rule, one registry branch and their helpers. No document, template, form or profile list changes.

## Interfaces & Data Structures

- `scripts/document_contracts.py`: `template_definition_record(raw_registry: Mapping[str, Any], profile_id: str) -> dict[str, Any]`, which raises for a profile that is not a template or carries no definition; `REGISTRY_TEMPLATE_RECORD` and `REGISTRY_TEMPLATE_EXTENSION` in `current_registry_diagnostics`, evaluated with `scripts/json_schema_validation.py`; `_table_diagnostics` without its heading-line branch.
- `scripts/validate-markdown-profiles.py`: the table check reads a form section only; `BODY-TABLE-SECTION` no longer exists.
- `tests/test_common_form_tree.py`: over every template profile with a definition in the repository registry, the record has exactly the 19 keys, passes the schema copy with the tolerance for a role without a form, has `role` equal to `document_role`, `headings` equal to the form tree, `metadata` names equal to the profile's key lists and equal `headings`, `extensions` and `contract_version` across the templates of one role. The set of templates without a definition equals the SDLC templates that phase 3 still owns, read from the landed state.
- Negative tests, each failing first: a definition without `contract_version` fails `REGISTRY_SCHEMA`; a `COMMON-DOC-FORM-1` value that differs from `common_forms.version`, a value outside the grammar and two different values on one role each fail `REGISTRY_TEMPLATE_RECORD`; a record with a missing field, an added field, a `Release` role, an H3 with children or an H2 with a parent fails the schema; an empty `headings` on a role that has a form fails; a `provider-native` definition without `headings_extension`, with a field missing, empty, whitespace-only or not text, with an extra or unknown key, with a wrong `id`, with an `owner` outside that set (for example `nobody`, failing first; `platform` and `buenhyden` pass), or with the record on a role that has a form or on a profile whose `document_role` is not `provider-native` fails `REGISTRY_TEMPLATE_EXTENSION`, and the same definition with the complete record passes; a complete record plus another schema finding of the same definition still fails; a table on a role without a form fails `REGISTRY_TABLE_SECTION`; the pinned SHA-256 of the schema copy fails on any byte change.

## Edge Cases & Error Handling

- A template without a definition (an SDLC template until its phase-3 package) has no record: the function raises for it and the check skips it.
- The Codex agent template is TOML with frontmatter mode `absent`; its `metadata` is empty, which the package schema allows.
- A table whose `section` names a `local_h3` extension id passes, because the package schema asks only for a non-empty string; the existing `REGISTRY_TABLE_SECTION` check still ties it to the form.
- A source profile with no lifecycle domain (the README, `AGENTS.md` and `provider-native` profiles) gets a `lifecycle` sentence that says so; the field is never empty.
- A registered `local_h3` title is an `extensions` item, not a `headings` item, so `headings` equals the form's own sections.
- The counts of forms, definitions and templates are read from the landed state of SPEC-0188 to SPEC-0195; none is taken from the pre-approval read.

## Failure Modes & Fallback / Human Escalation

If a derived record of a real template fails the schema in any way other than the tolerated `headings` finding of a role with a complete extension record, the cause is registry data that another package owns (a form section or a key entry); the author stops and asks the user and does not edit a form here. If any `tables[].section` of the landed registry still starts with a heading marker, the heading-line path has a consumer and the cleanup stops. If a strict document validator gains or loses a diagnostic, the change is wrong and is reverted to the last passing step. After two failed attempts with no new information the author stops and reports a repository defect.
