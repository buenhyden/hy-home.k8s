# Workspace Engineering External Research Refresh Implementation Plan

## Global Constraints

Inherit the [Spec](spec.md)'s exact write and no-observation boundaries. The direct user request authorizes external research, scoped document editing and local commits; it does not authorize runtime investigation, policy changes, push, PR, merge or cleanup of the retained worktree. Use one canonical Task, existing pack/member identities and no duplicate execution tree.

## Overview

Refresh the single workspace engineering pack with primary external evidence and concrete next-cycle scope questions. Complete only after all acceptance criteria, independent review and final full QA pass; preserve any unresolved external limitation explicitly.

## Verification Plan

Use [Spec commands](spec.md#verification-commands) resolved through the current validation registry. Targeted baseline checks precede edits; evaluate changed document profiles, headings, links/anchors, identity/lifecycle, placeholder absence and scope. Quick checks working-tree changes; staged checks the exact reviewed index for every logical commit; validate the actual UTF-8 message and commit through active hooks. Final full includes its own unit discovery and manual all-files pre-commit once. Record baseline defects separately without unrelated repairs or softened results. Task-only final evidence changes receive focused revalidation and a separately identified snapshot.

Use the bootstrap contract commit, then bundle research members, central indices, navigation and execution evidence into one coherent research commit. Shared source/claim/question relationships make artificial topic commits inconsistent; final handoff may be a separate validated evidence update. Never stage all paths blindly or leave blank templates. Initial states are recorded before activation; direct authorization supplies approval evidence for the later legal transition.

## Risks & Mitigations

| Risk | Mitigation and owner |
| --- | --- |
| Source churn, missing immutable revisions or access limits | Researcher records products, access dates, exact limits and bounded alternative evidence |
| External facts accidentally read as local findings | Writer uses explicit unobserved wording; reviewer checks every scope result |
| Shared IDs/anchors drift during parallel work | Integrator reserves IDs and owns final coverage and exact consumer cutover |
| Historical facts erased by current-first rewriting | Writer preserves dates and corrections under historical sections; reviewer checks disposition coverage |
| Scope expansion after QA baseline failure | Integration owner records failure and next owner; no policy, runtime or implementation repair |
| Context loss or misleading completion | Task stores command/snapshot results, approval boundaries, rollback and next owner |

These are research-delivery risks. No cluster, provider or hosted configuration risk has been observed in this cycle.

## Completion Criteria

All six Spec criteria have concrete evidence; U01–U39 and topic detail are covered; required QA and independent review are satisfied; external uncertainty remains bounded without masquerading as completed investigation; logical commits are coherent. Task records baseline/branch, changes, major external corrections/conflicts, question entrypoints, lane results, reviewer, commit SHAs, final Git status, bounded rollback and next owner. Branch/worktree remain; push/PR/merge are not attempted.
