# W03 Work Ledger Contract Technical Specification (Spec)

## Overview

This approved change contract is package 1 of the GOV-06 work residue ledger of the W03 stage of the external v14.7 execution package. It closes the first half of handoff W03-H30 (W03-D25): it changes only requirement, architecture and governance text, so that the later package 2 may build the ledger. The 2026-11-13 conformance audit found that REQ-0003 FR-0019 and FR-0022, its Scope and Non-goals and its Traceability, and the no-ledger clauses of ADR-0036, ADR-0047 and ADR-0048 disclaim a ledger (only the FR-0022 check cell, "No ledger file exists", is broad), while v14.7 asks for one machine ledger from which unfinished, adoption and survey state is derived and which detects residue that exists only in Markdown or only in JSON. v14.7 also forbids a competing progress ledger (GOV-03, SDLC-04), so the repository rule narrows from "no ledger" to "no competing progress ledger". The user decided on 2026-11-13, and the decisions are recorded in the [SPEC-0161 Task](../0161-w00-v14-7-delta-intake/tasks/tsk-0001-w00-v14-7-delta-intake.md) with this package's commit as W03-D37 to W03-D40: W03-D37, one JSON ledger and its schema hold residue only (open handoffs, conflicts, adoption items and survey items); Task rows and EVD rows stay the only owner of execution state, a terminal entry needs a closure reference to an EVD row, and adoption entries reference the registry's `shared_contract` and `common_forms` instead of copying them; W03-D38, views are derived on demand by a script in the manner of `scripts/document-backlinks.py`, no copy is committed, and closed entries are pruned to Git history; W03-D39, the ledger is seeded from current truth, stale and historical rows are closed by Resolves EVD rows or registered historical tables, and nothing recorded is rewritten; W03-D40, a new scoped-amendment ADR narrows the no-ledger clauses and the text below follows it. The [Task](tasks/tsk-0001-w03-work-ledger-contract.md), created in the first commit, records execution and the [Plan](plan.md) orders the work. Package 2 (W03-H30) builds and seeds the ledger.

## Contracts

- **New ADR.** `ADR-0060` "Work Residue Ledger Amendment", profile `sdlc/architecture-decision`, modeled on [ADR-0055](../../02.architecture/decisions/0055-governance-decision-current-state-amendment.md). It does not replace a paragraph; it narrows by dated clarification only. It narrows the no-ledger reading of: ADR-0036 lines 60-64 (the retired memory structure; the claim there that the governance validator fails closed is not repeated, and the clarification cites the guards that exist: `scripts/validation/repository/quality.py` lines 347-348, which refuse a tracked `progress.md`, and `tests/test_common_agents_document_routes.py`); ADR-0047 Decision 4's "without a second state ledger" (line 95) and Non-goal "creates no central progress ledger" (line 127); ADR-0048's Non-goal "permanent progress ledger" (line 183); and ADR-0031's execution-instance and "roster" clauses (lines 20, 35, 113 and 122: a roster copies instance state, and the residue ledger holds residue pointers only). Each reads: no competing progress ledger of execution state, and the work residue ledger of `ADR-0060` is not one. ADR-0047 Decision 4's knowledge surface holds no residue state. Everything else in the four ADRs stays accepted. The ADR also fixes the ledger location: not under `memory/`, no file named `progress.*`, and a registered document route when the file lies under `.agents/`. No Tombstone or archive record is added. Its Affected Spec link names this package and is replaced at the package exit (the ADR-0057 exit check).
- **Ledger rule (ADR decision text).** One JSON ledger with its schema holds work residue only: open handoffs, conflicts, adoption items and survey items. The Task and its EVD rows remain the only owner of execution state, status, evidence and acceptance. A terminal entry carries a closure reference to an EVD row. Adoption entries reference `shared_contract` and `common_forms` of `docs/99.templates/registry.json` by key and copy none of their values. Views are derived on demand by a script like `scripts/document-backlinks.py`; no view is committed. Seeding takes current truth: stale or historical rows are closed by Resolves EVD rows or registered historical tables, and no recorded row is rewritten. Stage 90 is excluded.
- **Entry fields and state.** An entry holds an identity, a kind (handoff, conflict, adoption or survey), a state, an owner, a resume condition, a source reference and, when terminal, a closure reference to an EVD row. The entry `state` is only open or terminal; it is compared with the Task and EVD rows (identity, state, owner and resume condition must agree) and never copies a Task status such as `draft` or `in-progress`. For residue the ledger entry is authoritative, and the Task Handoff rows point to it (SDLC-04) once package 2 exists.
- **Retirement.** A terminal entry is pruned no later than the owning package's exit commit; its closure reference is valid only until then, and Git history recovers it afterwards.
- **REQ-0003.** FR-0019 (line 72) keeps its sentence and is stated as a must that also covers the positive GOV-06 obligation: residue (unfinished, adoption and survey) is held in the work residue ledger; the ledger and the Task Handoff rows agree on identity, state, owner and resume condition; and Markdown-only residue, JSON-only completion and a terminal entry without an EVD closure reference are refused. It is not execution state and not a permanent roster of tranche, follow-up and succession history. Its own check cell reads "Built by the W03-H30 package 2; until then no ledger file exists and Plan/Task review shows package-local state." FR-0022 (line 75): "The removed shared progress ledger is not restored as a new current owner." becomes "The removed shared progress ledger is not restored as a new current owner; the work residue ledger of ADR-0060 holds residue only and never execution state." Its check cell becomes "No progress ledger exists; memory entries carry no Task status; the work residue ledger carries no Task status (checked by package 2)." Scope and Non-goals (line 119) gains that the work residue ledger is neither claimed as the removed ledger nor a parallel registry; line 121's "the single machine ledger for unfinished, adoption and survey state (FR-0019, FR-0022) agrees with v14.7 and stays not adopted" becomes adopted through SPEC-0185 and W03-H30 package 2. Line 143's "package-local unfinished ownership" gains "with the residue pointer in the work residue ledger". Traceability line 178 reads "No competing progress ledger exists; the work residue ledger holds residue only, and memory entries are never Task status or evidence." Line 175 stays.
- **AD-0006.** Line 41 gains "; the work residue ledger of ADR-0060 holds residue only and is not one". Line 95 gains "except residue pointers held in the work residue ledger". ## Core Design

[AD-0006](../../02.architecture/descriptions/0006-workspace-agent-governance-platform.md) owns the governance view and its sentences change as stated; no component is built. The new ADR is a scoped amendment like ADR-0055: one record that narrows named clauses and leaves the predecessor bodies as decision history.

## Data Modeling & Storage Strategy

None in this package: no ledger file, schema or registry data. The entry fields above are the contract package 2 implements.

## Interfaces & Data Structures

None in this package. Package 2 owns the schema, the derivation script and its validator; this package fixes only the rule they implement.

## Edge Cases & Error Handling

- Registry-owned contracts: an adoption entry points to `shared_contract` or `common_forms` by key; copying a value is a ledger defect.
- A ledger entry that carries a Task status, evidence or approval is execution state and is refused by the rule.
- Stage 90 audit, research and data documents stay evidence and are never ledger entries.
- A cited line that moved is re-verified before the edit; the sentence, not the line number, decides the target.

## Failure Modes & Fallback / Human Escalation

If any amended text could be read as restoring a progress ledger, or as making the ledger an owner of execution state, the author stops and asks the user. If a diagnostic appears in any strict document validator, the change is wrong and is fixed before commit. If the user declines ADR-0060, the implementation commit is reverted as a whole.
