# W03 Work Residue Ledger Technical Specification (Spec)

## Overview

This approved change contract is package 2 of the GOV-06 work residue ledger of the W03 stage of the external v14.7 execution package. It closes handoff W03-H30 (W03-D25). Package 1 (SPEC-0185, merged to `main` at `8231f782` and closed) changed the requirement, architecture and governance text, and the accepted [ADR-0060](../../02.architecture/decisions/0060-work-residue-ledger-amendment.md) fixed the rule; this package builds what they define: one JSON ledger with its JSON Schema, an on-demand view script, a drift and closure validator registered as a gate with tests, and the seed from current truth. The user's decisions of 2026-11-13 are recorded in the [SPEC-0161 Task](../0161-w00-v14-7-delta-intake/tasks/tsk-0001-w00-v14-7-delta-intake.md): residue only, with Task rows and EVD rows the only owner of execution state (W03-D37); views derived on demand, no committed view and closed entries pruned to Git history (W03-D38); seeding from current truth with stale and historical rows exempt and no recorded row rewritten (W03-D39); the name "work residue ledger" and Stage 90 excluded (W03-D40). A read of `main` at `8231f782` found that the `sdlc/task` profile registers no handoff table: the 33 handoff rows (W02-H01, W03-H01 to W03-H32) and the 6 conflict rows of the SPEC-0161 Task sit in free-form tables with no state cell, most with owner and resume condition in one cell, and the `W03 Decisions` table holds rows of four and five cells under one four-column header. The four-field comparison that REQ-0003 FR-0019 requires therefore needs a row form a reader can parse. On 2026-11-13 the user decided that form and the ten other design choices of this package as W03-D47, recorded in the SPEC-0161 Task with this package's commit: the ledger location, the live `Residue Handoff` table, its registration in the Stage 99 registry, the recognition of residue tables, entries without a Task row, the seed scope, the refusal of a package exit with open residue, the copied-value check, identity, the closure row result, and the script and suite layout. The [Task](tasks/tsk-0001-w03-work-residue-ledger.md) records execution and the [Plan](plan.md) orders the work.

## Contracts

- **Ledger file (W03-D47).** One file, `docs/03.specs/work-residue-ledger.json`, holds `$schema`, `schema_version` and `entries`, sorted by `id` with no duplicate. It is not under `memory/`, is not named `progress.*` and is not under `.agents/`, so the location rule of ADR-0060 needs no document route. Stage 03 holds the Task rows it must agree with and its writers already own them; Stage 99 is the protected contract surface, where every residue edit would be a contract change (Stage 99 rule 1), and `scripts/` holds executable validation only. The schema is a contract and sits in `docs/99.templates/contracts/`, which the `stage99-machine-contracts` route already covers.
- **Schema.** JSON Schema Draft 2020-12 like the two schemas beside it, every object closed with `additionalProperties: false`. An entry holds `id`, `kind` (`handoff`, `conflict`, `adoption` or `survey`), `state` (`open` or `terminal`), `owner`, `resume_condition`, `source` and, exactly when `state` is `terminal`, `closure`. `source` holds `path` and, exactly when `kind` is `adoption`, `registry_key` (`shared_contract` or `common_forms`). `closure` holds `path` and `evidence` (an `EVD` row ID). No key exists for a status, result, evidence text, approval, acceptance, title or description: the Task owns those, and the entry is a pointer.
- **Residue rows in a Task (W03-D47).** A Task writes residue in one table under the H3 `Residue Handoff`, which sits under the H2 `Task Evidence` after the evidence table, as every appended H3 of the SPEC-0161 Task does: the evidence reader takes the first table of that section, `common_forms` has no Task form yet and the `sdlc/task` profile fixes H2 names only. Its columns are `ID`, `Residue`, `State`, `Owner`, `Resume condition`, `Closure`, in that order. `State` is `open` or `terminal`; `Closure` is `none` or one `EVD` ID of the same Task. `ID`, `State`, `Owner` and `Resume condition` equal the entry's `id`, `state`, `owner` and `resume_condition` as text with surrounding whitespace removed and no other normalization. `Residue` is the Task's own description and is not compared. A row's `State` and `Closure` cells change in place when it closes; its `ID` never changes.
- **Registry block (W03-D47).** `work_residue` in the Stage 99 registry holds `task_table` (the host section `Task Evidence`, the heading and the columns above, so the phase-3 Task form of W03-H02 moves the host by a registry edit) and `historical_tables` (each a Task `path` and a `heading`), following the path lists of `readme_navigation`. The ledger and schema paths are constants of the gate.
- **Drift and closure gate (W03-D47).** `python3 scripts/validate-work-residue-ledger.py --root .` reads the files under the root only, with no Git history and no network. A residue table is a table in a Task under a heading that contains `Handoff` or `Conflicts`, or one in which the first cell of any row, with surrounding whitespace removed, matches `^W[0-9]{2}-H[0-9]{2}$` in full. A decision row such as `W03-D40` does not match; `W03 Decisions` is a residue table because it also holds `W03-H01` to `W03-H32`, and its registration by path and heading covers the whole table. A handoff or conflict entry is sourced in a Task; an adoption entry may be sourced at `docs/99.templates/registry.json` and a survey entry at a current non-Task document, and those two need no row. The gate refuses: a ledger that fails its schema (`RESIDUE-SCHEMA`); an open live row with no entry, and a residue table that is neither the live table nor registered historical (`RESIDUE-MARKDOWN-ONLY`); an open entry sourced in a Task with no open live row of its `id` (`RESIDUE-JSON-ONLY`); a difference in state, owner or resume condition, naming the field (`RESIDUE-DRIFT`); a terminal entry whose `closure` does not name a `PASS` EVD row of a current Task, whose `closure.path` differs from a Task `source.path`, or whose live row is not terminal with the same EVD ID (`RESIDUE-CLOSURE`, the JSON-only completion); a `source.path`, `closure.path` or registered historical table that does not resolve under the root, a path under `docs/90.references/` or `docs/98.archive/`, or a handoff or conflict entry sourced outside a Task (`RESIDUE-SOURCE`). A terminal live row whose `Closure` resolves needs no entry, so pruning is legal. A source or closure Task that left the tree fails `RESIDUE-SOURCE`, which enforces both the pruning of terminal entries and the transfer or closure of open ones before a package exit.
- **Residue-only guards (W03-D47).** `RESIDUE-REGISTRY-COPY` refuses an adoption entry whose `registry_key` is absent from the registry and any entry string that contains a contract identifier, digest, source revision or approval reference of `shared_contract` or `common_forms`. `RESIDUE-TASK-STATUS` refuses a `State` cell or entry `state` outside the two words; the test feeds every value of the `sdlc/task` status domain and of the evidence result states read from the registry, never a copied list.
- **View (W03-D38).** `python3 scripts/work-residue-ledger.py --root . [--kind K] [--state S] [--owner O]` prints one line per entry (`id`, `kind`, `state`, `owner`, `resume_condition`, source) to standard output, writes no file and exits 2 with `FAIL WORK-RESIDUE` when the ledger is unreadable, in the manner of `scripts/document-backlinks.py`. No view is tracked.
- **Seed (W03-D39, W03-D47).** The implementation commit appends the `Residue Handoff` table to the SPEC-0161 Task with one row per item that is open in current truth in any table of that Task, citing the legacy row in `Residue` and keeping its recorded ID (a row that has none takes the next number of its stage series), and writes the matching entries; The two adoption entries follow the same identity rule and take no decision ID: the `common_forms` entry is `W03-H19` (the missing adoption record of COMMON-DOC-FORM-1), and the `shared_contract` entry (the six `unverified` approval facts) has no recorded handoff row and takes the next W03 handoff number. Both have a live row in the SPEC-0161 Task. The legacy tables that the gate recognizes (`Document Form Handoff`, `Stage QA Handoff`, `Conflicts`, `Stage Follow-up Handoffs`, `W03 Decisions`) are registered historical in the same commit. An appended EVD row (`Resolves none`) records the read: rows seeded per kind and per table and, for each row left unseeded, the evidence that closed it. No legacy cell is edited.
- **Retirement (W03-D38).** A terminal entry is deleted no later than the exit commit of the package whose Task holds its closure row; Git history recovers it.
- **Gate registration (W03-D47).** `scripts/validation/registry.json` gains the validator `work-residue-ledger` (lanes `affected` and `staged`, required, fallback `FAIL`, `repo-static`) in both profiles; a `review` surface for the ledger file; a `protected` surface with exact routes for the two scripts and the test module, which also selects `document-contract-tests`; and the validator on the `authored-documents` and `stage99-machine-contracts` surfaces, so a Task, schema or registry change runs it. The `authored-documents` and `scripts` routes exclude the new paths, keeping `uncovered=0 ambiguous=0`.
- **Text.** The FR-0019 check cell reads "The `work-residue-ledger` gate and `tests/test_work_residue_ledger.py`."; the FR-0022 check cell ends "the work residue ledger carries no Task status (`work-residue-ledger` gate)."; AD-0006 names the file. The work lifecycle and Stage 03 `AGENTS.md` say that residue is written as a `Residue Handoff` row and a ledger entry in the same change and that terminal entries leave before the package exit. The Task template gains an author prompt under `Task Evidence` and no visible table. The Stage 03 README must list the ledger in `Current Items`, in the tree and with its purpose: the README is a `common/readme-stage-index`, whose index `readme_navigation` marks complete, and the ledger is the first non-Markdown file directly in the Stage 03 folder.
- **This package's own residue.** W03-H30 and the `LEDGER` conflict are seeded open. After the user's acceptance an appended `PASS` EVD row in the SPEC-0161 Task closes them: their live rows become terminal with that EVD ID, and their entries are terminal in that commit and deleted no later than this package's exit, which shows the whole cycle on real rows.

## Core Design

[AD-0006](../../02.architecture/descriptions/0006-workspace-agent-governance-platform.md) owns the governance view and ADR-0060 the decision; no component of either changes. The gate adds no parser: it loads `scripts/validate-links-and-owners.py` as `scripts/document-backlinks.py` does and uses its `_exact_heading_section`, `_first_visible_table` and `task_base_evidence_rows`, checks the ledger with `schema_errors` of `scripts/json_schema_validation.py`, and reads through the bounded helpers of `scripts/validation/repository/bounded_io.py`. The view imports the gate's loader, so both read the ledger one way.

## Data Modeling & Storage Strategy

One tracked JSON file and one schema. An entry is seven fields at most and carries no description, so the ledger stays a list of pointers. The estimated seed is 55 to 70 entries (about 22 of the 33 handoff rows, 3 or 4 of the 6 conflicts, 2 adoption entries, and the still-open rows of Requirement Changes, Stage QA Handoff, Document Form Handoff and the Read Denominator); the Task records the counted numbers. Closed entries live only in Git history.

## Interfaces & Data Structures

- `docs/03.specs/work-residue-ledger.json`: `{"$schema": "../99.templates/contracts/work-residue-ledger.schema.json", "schema_version": 1, "entries": [...]}`.
- `scripts/validate-work-residue-ledger.py --root .`: exit 0 with a `PASS` line, exit 1 with one `FAIL <RULE> <path or id> <detail>` line per finding.
- `scripts/work-residue-ledger.py`: the view above.
- `docs/99.templates/registry.json` `work_residue`: `task_table` (`section`, `heading`, `columns`) and `historical_tables` (`path`, `heading`).
- Tests, on temporary trees and never over the repository (`tests/test_validation_tooling_ownership.py` refuses a test that reruns a gate over it): one failing-first case per rule ID; an agreeing ledger and Task pass; an empty ledger with no residue table passes; a pruned terminal row passes; each Task status value, a copied contract identifier, a Stage 90 source, an exited source Task and an unregistered `Handoff` table are refused; ordinary owner and resume-condition text, including the registry's owner name, `unverified` and a version string, does not trip the copied-value scan, and the gate run over the seeded tree, recorded in the Task, shows the same for every seeded entry; a `W03-D` first cell is not a handoff row and a `Residue Handoff` table outside `Task Evidence` is refused; the view filters by kind, state and owner and writes no file; the ledger path is not under `memory/` or `.agents/` and is not named `progress.*`.

## Edge Cases & Error Handling

- A legacy row and its live row share an ID inside one Task; identity is read from the live table only, and the legacy table is historical.
- `Residue Handoff` appearing twice in a Task is refused, because the reader accepts exactly one match.
- A registered historical table whose Task left the tree is refused until its registration is removed, so the registration leaves with the package.
- A transfer is one change: a new live row in the receiving Task, the entry's `source.path` updated, and the old row closed by an EVD row of its own Task.
- A Stage 03 README without the ledger in `Current Items` fails the complete-index rule, so the README entry lands in the implementation commit with the file.
- Moving registry lines can shift a baselined secret-scan finding; the baseline line moves in its own commit first (Stage 99 rule 6).
- Two packages that append entries rebase; sorted entries keep the diff local.

## Failure Modes & Fallback / Human Escalation

If seeding would need a recorded row rewritten, if the recognizer refuses a current document that holds no residue, if any text could be read as restoring a progress ledger or as making the ledger an owner of execution state, or if a strict document validator gains a diagnostic, the author stops and asks the user. Rollback is the revert of the implementation commit: the ledger, schema, registry block, gate, view, tests and registration leave together, and the SPEC-0161 Task loses only appended lines.
