# W03 Relationship and Link Contract Technical Specification (Spec)

## Overview

This approved change contract is the first phase-3 package of the W03 stage of the external v14.7 execution package. It closes handoffs W03-H08 and W03-H16 recorded in the [SPEC-0161 Task](../0161-w00-v14-7-delta-intake/tasks/tsk-0001-w00-v14-7-delta-intake.md): no current contract states, for each document relationship, its cardinality, direction, canonical owner and derived consumers, and none defines the four link types (normative, evidence, historical, navigation) or the seven relation kinds (authority, structural ownership, constraint, traceability, promotion, supersession, change impact), although W03-D11 already places links by type. The six SDLC forms of W03-H02 (Requirement, Architecture, ADR, Spec, Plan, Task) host these relations in their Traceability, References, Promotion Map and Handoff sections, so the contract comes first and the five form packages that follow place content by it, in the order W03-D49 fixes. The relations themselves already exist: direct parents in `parent_ids`, requirement basis and design constraints in the `Lifecycle Traceability` tables, promotion in the Plan `Promotion` table, and supersession in `supersedes` and `superseded_by`. This package records them in one machine owner, cites the checks that already enforce them, and adds one check found missing: a link fragment is not compared with the headings of its target. A read of `main` at `de64c58d` (after SPEC-0186) with an approximate slug rule found about 960 fragment links to tracked Markdown outside `docs/98.archive/`, three of them broken, and 125 that target Stage 01 to 03 documents, 57 of which name the Spec H2 anchor `success-criteria--verification-plan` that the Spec form will rename. The Spec and Plan form package (package 5 of W03-D49) repoints those 57 links, the ones in frozen records under the W03-D50 exemption. On 2026-11-14 the user decided the phase-3 order and grouping (W03-D49), the migration route of the SPEC-0161 package (W03-D50), the three design choices of this package (W03-D51) and the form details of the later packages (W03-D52). On 2026-11-14 the user also decided W03-D65, that where the W03 requirement text (REQ) and a current repository rule conflict, the REQ text governs ("`W03 프롬프트에 작성된대로`"); this package is the first of the affected packages to land, so its commit records W03-D49 to W03-D52 and W03-D65 in the SPEC-0161 Task. This package applies W03-D51 and the DOC-09 and cycle clauses of REQ below; the later packages apply W03-D50, W03-D52 and the four resolutions of W03-D65. The [Task](tasks/tsk-0001-w03-relationship-link-contract.md) records execution and the [Plan](plan.md) orders the work.

## Contracts

- **Contract home (W03-D51).** A new optional top-level registry section `relationship_contract`, checked by the strict registry validator, as SPEC-0181 did for `frontmatter_keys`; this follows REQ-0003-FR-0012 (one machine owner of document form and lifecycle edges) and the W03 task's instruction to revise the registry's own parent, cardinality and relationship definitions. A prose table in the document authoring policy only and a separate JSON file under `docs/99.templates/contracts/` were not chosen.
- **Relation kinds (W03-H16).** `relation_kinds` holds exactly seven entries: `authority`, `structural-ownership`, `constraint`, `traceability`, `promotion`, `supersession` and `change-impact`. Each states its meaning, its direction (which document names which) and who writes it. REQ:645 (DOC-09) requires Authority, Ownership, Reference, Traceability and Change Propagation to be separated by relation ID, direction and owner, so every kind that REQ names has a relation entry of its own (see the next bullet).
- **Relations (W03-H08).** `relations` holds exactly eight entries, each with one kind, its `direction`, its source and target profiles, the cardinality on each side, one canonical owner per source profile, its reverse view, its consumer paths, the rules that check it with the script that holds each rule, a positive and a negative test, and its known gaps.
  - DOC-09 mapping (REQ:645): Authority is kind `authority` (relation `policy-authority`), Ownership is `structural-ownership` (`parent`), Reference is `constraint` (`design-constraint`, with the four link types stating which references carry authority), Traceability is `traceability` (`requirement-basis`) and Change Propagation is `change-impact` (`consumer-impact`); `promotion` and `supersession` are two further kinds that REQ:292 (the relationships row) lists, and its verification evidence is the relation `verification-evidence` below (kind `traceability`, a Task back to the Spec criterion it verifies). Each relation has one ID, one direction and one canonical owner, and no relation shares an ID with a kind.
  - `parent` (`structural-ownership`): a Task names its Plan and a Plan names its Spec; exactly one parent per child; the owner is the child's frontmatter `parent_ids`, derived from the package path; checked by `PARENT-IDENTITY` and `TASK-PARENT-APPROVAL`.
  - `requirement-basis` (`traceability`): a Spec names requirement members in the `Requirement ID` column and an architecture description in `Upstream requirement`; one or more per source, any number per target; checked by `BODY-CONTRACT-IDENTIFIER` and the body-contract link rules (`BODY-LINK-BROKEN` and the source link and source profile rules).
  - `design-constraint` (`constraint`): the Spec `Architecture` column, the architecture description `ADR / Spec` column and the ADR `Decision lineage` and `Affected Spec` columns; any number on each side, never a second parent; the Spec column has no link check today, which the entry records as a gap.
  - `promotion` (`promotion`): a Plan names the current owner that receives each durable contract in its `Promotion` table, or the explicit none row; the current owner holds the content and the Task holds the receipt; checked by `PLAN-PROMOTION`.
  - `supersession` (`supersession`): a successor names its predecessor in `supersedes`; where the lifecycle domain has a `superseded` state the predecessor names the successor in `superseded_by` and both sides change in one commit; an accepted ADR is never edited, so its successor alone carries the relation; checked by `LIFECYCLE-EVIDENCE`, which also refuses a chain that ends without a current document and, from this package, a cycle (see Cycle detection).
  - `verification-evidence` (`traceability`): a Task names the Spec criterion that each of its evidence rows and each of its acceptance rows verifies; direction Task to Spec criterion; one or more per Task row, any number per criterion; the owner is the `Criteria` column of the Task Evidence table and the `Criterion` column of the Criterion Acceptance table (carrier `body_contract`); source profile `sdlc/task`, target profile `sdlc/spec`; checked by the body-contract link rules (`BODY-LINK-BROKEN` and the source link and source profile rules) and by `TASK-EVIDENCE-COLUMNS`, which is read at implementation before it is cited; the reverse view is derived by `scripts/document-backlinks.py`. Gap recorded: whether a criterion identifier names a criterion that exists in the parent Spec is read at implementation and recorded as covered or as a gap.
  - `policy-authority` (`authority`): a template or document names the policy owner whose rule it applies; direction source to policy owner; one or more per template, any number per owner; the owner is the `policy_refs` of the template's `template_definition` (carrier `registry_key`) and, for a governed document, its authority section; the source profiles are the template profiles that carry a `template_definition` and the target profiles are the `governance/*` and policy profiles; checked as to shape by `REGISTRY_SCHEMA` and as to links by `LINK-BROKEN` and `LINK-STAGE-BOUNDARY`; the record test of SPEC-0196 is its first consumer. Gap recorded: no rule checks that a `policy_refs` path exists, which this package does not add.
  - `consumer-impact` (`change-impact`): a frontmatter key or a TemplateDefinition names the paths that must change with it; direction owner to consumer; one or more per owner, any number per consumer path; the owner is `consumer_paths` of the key entry in `frontmatter_keys` and of the `template_definition` (carrier `registry_key`); the source profiles are the template profiles that carry a `template_definition`, the targets are paths, so `target_profile_ids` is empty and the entry names the path set; checked by `REGISTRY_KEY_CONSUMER` and `REGISTRY_KEY_TEST` (SPEC-0181) for keys; the reverse view is read from the registry entry and `scripts/validate-affected-surfaces.py` maps a changed path to its validators. Gap recorded: the `consumer_paths` of a definition are not checked for existence.
- **Cycle detection (REQ:245).** REQ names four violations: a cycle, two parents where a Task or Plan needs one direct owner, a reverse-field mismatch, and history read as normative. A read of `81096a83` found three already enforced and one gap. Two parents: `PARENT-IDENTITY` compares `parent_ids` with the one identity `direct_parent` derives from the package path, so a second parent fails, and a parent cycle cannot be written for a Task or Plan because the parent is derived from the path and a Spec carries no `parent_ids`. Reverse-field mismatch: `require_reciprocal_supersession` and `LIFECYCLE-EVIDENCE`. History read as normative: the `normative` link type and `LINK-STAGE-BOUNDARY`. The gap: no rule detects a cycle among documents. `_terminal_supersession_evidence` walks a chain with a visited set, so a cycle made only of superseded documents fails, but only as a chain that ends without a current document; a self-reference or a cycle among documents that are not superseded, and any cycle in a lifecycle domain without a `superseded` state, pass. At `81096a83` six documents carry `supersedes` and none carries `superseded_by`, so the new check has no existing case to repair. This package adds two rules:
  - `REGISTRY_RELATION_CYCLE` in `current_registry_diagnostics`: the profile graph of the `relations` whose kind is `structural-ownership` (an edge from each source profile to each target profile) has no cycle and no self-edge; a `supersession` relation is a same-profile relation whose source and target profile are equal, so it would fail on the repository registry and is left to the document walk below, and a source profile of a `structural-ownership` relation has exactly one owner entry per relation (one direct owner, never two). Test: a synthetic registry whose `parent` relation names Plan as the parent of Task and Task as the parent of Plan fails; one with two owner entries for the Task fails; a self-edge fails; the repository registry passes.
  - `LIFECYCLE-EVIDENCE` in `scripts/document_lifecycle.py`, observed as `supersession cycle`: a document reachable from itself fails, in any lifecycle domain and with any status. The walk treats `supersedes` and `superseded_by` as one successor graph (an edge from the document that names to the document named, in either field), because Guide, Policy and Runbook carry only `superseded_by`. It runs over every document of the proposed tree on every run, not only the changed ones, and a self-reference is detected before the visited set can skip it. Tests, failing first: a self-reference; a two-document loop and a three-document loop of current documents; a cycle in an unchanged part of the tree while a different document changes; a loop that uses only `superseded_by`; and a Task whose `parent_ids` names itself, which fails `PARENT-IDENTITY`. Passing: a linear chain and a diamond (two successors that name one predecessor). A multiple requirement basis or design constraint on one document is never read as a second parent.
- **Written once (W03-D51).** Each relation is written by its source document and every reverse view is derived by `scripts/document-backlinks.py`; the two reciprocal carriers that current checks require stay and are recorded as such, namely `superseded_by` (one relation updated on both sides) and the Requirement `Downstream owner` column, whose removal the Architecture form package (SPEC-0197) owns (REQ:645, REQ:250). Neither carrier is removed here and neither becomes a second canonical relation.
- **Link types (W03-H16).** `link_types` holds exactly four entries, each with its meaning, direction, whether it is required, whether it carries authority, what it pins, its checks, tests and gaps.
  - `normative`: names the current owner whose rule applies, by its identity and, where the owner is versioned, the version or scope that applies; it carries authority, so its target is a current document, never history; checked by the body-contract link rules, which admit only the profiles a column allows, and by `LINK-STAGE-BOUNDARY`.
  - `evidence`: pins what was observed (revision, input, result and location); it carries no authority; checked by the Task evidence rules, including `TASK-EVIDENCE-LOCATION`.
  - `historical`: names a `commit:path` or an `Archived Lineage` row for recovery and is marked non-authoritative; reachability stays a manual review and links into `docs/98.archive/` stay unchecked (ADR-0053).
  - `navigation`: promises only that the path and the anchor exist; checked by `LINK-BROKEN` and the README navigation rules for the path, and by the new fragment check for the anchor.
- **Registry checks.** The strict registry validator refuses a missing section, an entry set other than the eight relations, seven kinds and four link types named above, a relation whose `direction` is not one of the enumerated values `source_to_target` and `owner_to_consumer`, a relation whose kind, profile, frontmatter key or body-contract column is not declared in the registry (`REGISTRY_RELATION`, which also checks `direction`), a consumer or check path that is not an existing regular file or a rule identifier that does not occur in its named script (`REGISTRY_RELATION_CONSUMER`), a test reference whose module or test does not exist (`REGISTRY_RELATION_TEST`), and an ownership graph that is not a forest (`REGISTRY_RELATION_CYCLE`, see Cycle detection). A comparison-base registry without the section still loads.
- **Missing check (W03-D51).** Only the fragment check is added now. `LINK-FRAGMENT` in the link validator refuses a repository-local link whose fragment names neither a heading slug nor an explicit HTML anchor of its target, for same-file and cross-file links to tracked Markdown; the broken fragments it reports are repaired in the same change. This follows W03-H16 (add checks only where missing) and DOC-07 (anchors), and it protects the heading renames of the form packages. The Spec `Architecture` link check is not added in this package.

## Data Modeling & Storage Strategy

Registry data: one section with seven kind entries, eight relation entries and four link-type entries. Code: four registry diagnostics, one link diagnostic and one lifecycle observation. Documents: fragment-only repairs and two policy texts.

## Interfaces & Data Structures

- `relationship_contract.relation_kinds[]`: `id`, `meaning`, `direction`, `owner`.
- `relationship_contract.relations[]`: `id`, `kind`, `direction` (`source_to_target`, or `owner_to_consumer` for a path target), `source_profile_ids`, `target_profile_ids` (empty for `consumer-impact`, whose targets are paths), `cardinality` (`per_source`, `per_target`), `canonical_owners[]` (`profile_id`, `carrier` of `frontmatter`, `body_contract`, `section` or `registry_key`, and the key, column or heading), `reverse_view`, `consumer_paths[]`, `checks[]` (`rule_id`, `path`), `positive_test`, `negative_test` (`module`, `test`) and `gaps[]`.
- `relationship_contract.link_types[]`: `id`, `meaning`, `direction`, `requiredness`, `carries_authority`, `pinning`, `checks[]`, `positive_test`, `negative_test` and `gaps[]`.
- `scripts/document_contracts.py`: the loader exposes the section on the registry object, and `current_registry_diagnostics` gains the four rules, so they run from the strict registry validator and never on the load path.
- `scripts/validate-links-and-owners.py`: `LINK-FRAGMENT` in the link pass, with heading slugs taken from the rendered heading lines outside fenced blocks, lower-cased, punctuation removed, spaces as hyphens and a repeated slug numbered, plus explicit `id` and `name` anchors.
- `scripts/document_lifecycle.py`: the supersession cycle observation of `LIFECYCLE-EVIDENCE`, one successor walk over `supersedes` and `superseded_by` across the whole proposed tree, with a visited set that never skips a self-reference.
- Tests: each registry rule fails first on a synthetic registry and then passes on the repository registry; a broken same-file and a broken cross-file fragment fail; a heading slug, a numbered repeat, an explicit anchor and a Korean heading pass; a fenced heading is no anchor; a template placeholder, an external link, a non-Markdown target and an archive target are not checked. The `supersession` entry keeps a test for a lifecycle domain without a `superseded` state, where the successor alone carries the relation.

## Edge Cases & Error Handling

- markdownlint `MD051` is disabled in this repository and compares same-file fragments only, so it cannot stand in for the new check and stays as it is.
- A fragment into a non-Markdown file (for example a source line) and a fragment into `docs/98.archive/` are not checked; a template's placeholder link keeps its existing exemption.
- The Plan `Promotion` table is read by a script and not by a body contract, so its owner entry uses the `section` carrier and names the heading and header that `PLAN-PROMOTION` reads; the Plan form package changes that entry with the reader.
- A relation with two source profiles carries one owner entry for each; multiple requirement or design references on one document are never a second parent.
- SPEC-0191 merges before this package and also adds an optional top-level registry key (`work_residue`) with its schema property, so both packages edit the `OPTIONAL_TOP_LEVEL_KEYS` set of `scripts/document_authority.py`, the registry loader, the tests that pin the top-level key set and `scripts/validation/registry.json`; this package is rebased on `main` after it and adds its key beside that one.
- SPEC-0207 (the Registry Schema Version package, W03-D66) lands right after SPEC-0191 and before SPEC-0192 and every later package, so this package lands on a registry whose `schema_version` is the SemVer string `11.0.0`. **Expected bump: MAJOR.** This package adds `relationship_contract` as a new top-level key, which the strict loader (`validate_registry_authority` with `OPTIONAL_TOP_LEVEL_KEYS`) and the schema (`additionalProperties: false`) reject, so under REQ:878 and W03-D66 the step is MAJOR: the next MAJOR number over the value on `main` at landing (`12.0.0` when `main` holds `11.0.0`), with MINOR and PATCH reset to 0. The implementation commit applies the bump to the registry, the schema `const`, `REGISTRY_MAJOR`, `READABLE_REGISTRY_MAJORS` and the write guard constant, and the Task records the level and the reason as evidence; those files are added to this Spec's scope. The version-pinning tests derive their values from those constants (SPEC-0207), so none is edited here.
- The pre-approval counts used an approximate slug rule; the Task records the exact list the implemented check reports before any repair.

## Failure Modes & Fallback / Human Escalation

If the fragment check reports a broken fragment in a document that may not be edited (the Spec or Plan of a finished package, a terminal document, or a published member beyond its link destinations), the author stops and asks the user. If an entry cannot be written without changing what a current check enforces, or if any document outside the named scope gains a diagnostic, the change is wrong and is fixed before commit or taken to the user.
