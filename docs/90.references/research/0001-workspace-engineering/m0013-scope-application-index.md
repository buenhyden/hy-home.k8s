# Reference: Scope Application Index

## Overview

This index turns the pack's current external findings into bounded follow-up questions. It is the canonical detailed investigation ledger; topical reports own findings and concise question wording, and m0012 owns source/claim/request coverage. Every current application result is **not observed in this cycle**.

## Reference Type

Analytical scope and investigation routing over external research, with dated historical scope projections retained.

## Authority Boundary

The seven axes below organize questions; they do not define governance roles, scope membership, write ownership or permissions. Canonical role, governance and approved lifecycle owners retain those decisions. Candidate file types/selectors are hypotheses, not paths observed to exist. No runtime, hosted CI, model entitlement, billing, memory recall or cluster behavior was investigated in this cycle.

## Scope

The investigation spans organization/user, repository, directory/domain, task/session, provider/product, CI/delivery and cluster/environment. These are analytical axes, distinct from the older ten-governance-scope projection preserved below. An approved later work package must choose a bounded subset, evidence lane, permissions and responsible role before acting.

## Definitions / Facts

### Analytical axes and evidence contract

| Axis | What the investigation asks | Evidence boundary |
| --- | --- | --- |
| organization/user | Managed policy, account/client defaults, billing and authority | Public contract is external evidence; effective private/account state requires separate observation |
| repository | Canonical document, gateway, task and artifact ownership | Candidate selectors do not prove implementation or discovery |
| directory/domain | Closest instructions, domain knowledge and isolated responsibilities | Names and directories do not grant permission |
| task/session | Acceptance, loop budgets, checkpoints, compaction and handoff | Completion and recall require independent outcome evidence |
| provider/product | CLI, IDE, cloud, SDK, models, hooks and memory | Documented capability is version/surface-specific; installed behavior unobserved |
| CI/delivery | Exact bytes, trust, QA, artifacts, identity and promotion | Static workflow text is distinct from hosted results and effective gates |
| cluster/environment | Reconciliation, networking, storage, security and recovery | Manifests and documentation do not establish live behavior |

Each row binds a granular question to U/REQ/Claim/Source, analytic scope, canonical file type, candidate selector, evidence, validation/acceptance, approval/risk, current result, and next role/trigger. File-type and selector cells are code literals because no current existence observation was made. Roles are routing suggestions, never delegated permission. Pass criteria are proposals for a future authorized investigation, not results.

The four evidence axes remain separate: external Verified/Partial/Unverified/DEFER/Contradicted; source new/changed/unchanged/unreachable; workspace **not observed in this cycle**; actual document QA PASS/FAIL/SKIP/DEFER. No external unfinished item is filled with DEFER to imply completed research. All source identities and current request coverage are in [m0012](m0012-source-coverage.md#requirement-coverage-matrix).
