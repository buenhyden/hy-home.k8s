### Findings raised by the closing verification

Two defects surfaced only when the gate and the suite ran against the closing
change, and both are recorded because each overturned an earlier judgement.

`AGQC-LEGACY-OWNER` rejected AD-0006, not the two superseded ADRs that carry the
same removed path. ADR-0013 and ADR-0019 hold `status: superseded`, which the
registry classes as terminal, so `LIFECYCLE-TERMINAL-MUTATION` holds their bytes
fixed and `validate-agent-legacy-cutover.py` already excludes them from its
active-consumer scan. A superseded ADR records what was decided, not what is now
true. Editing one to refresh a path was attempted, failed closed, and was
reverted; only AD-0006, which is active and names owners in the present tense,
was corrected.

The suite, which the gate does not run, then rejected the closing change alone:
`STANDALONE_APPROVAL_STATEMENTS` carried twelve entries while the registry
declared four. The eight extras predate this Spec and are visible on `main`.
Seven of them, 0055 through 0061, pair with Spec bodies that still assert the
approval sentences, so declaring any one of those relations would have satisfied
`STANDALONE-EXECUTION-APPROVAL` with no human approving it; the eighth, 0043, was
a closed synthetic self-test relation. The statements were removed rather than
restated, which fails closed: a relation declared later must have its statement
authored then, with its own date. The test that had frozen the twelve now derives
the expected roster from the registry, so the two cannot drift apart again.

The standalone roster had two owners and no comparison, which is how that
divergence survived. ADR-0022, which is accepted and therefore current, linked
eleven Specs as typed standalone-execution relations; the registry declared four.
Measurement settled which owner was wrong. Declaring all eleven was attempted and
refused: 0057 through 0061 raise `STANDALONE-EXECUTION-RECIPROCAL` because their
Plans route Tasks through a README index instead of linking them, and 0058 also
raises `STANDALONE-EXECUTION-STATE`. Plan, Task and Spec are terminal in every
case, so the shape cannot be corrected. The registry held exactly the four
relations whose shape satisfies the contract, so the decision was over-claiming
and the decision was corrected: those seven are now named without links, which
records the execution without asserting a relation the registry cannot hold.
`STANDALONE-DECISION-ROSTER` now holds the two rosters equal, so a Spec linked by
the decision is a Spec the registry declares.

Removing the seven approval statements was therefore right for the wrong reason.
They were not stale junk; they matched ADR-0022. They were still a fail-open
surface, because the registry, not the decision, is what the validator reads.
0043 was different and plainly wrong: it is a tranche of PRD-0003 under AD-0006,
so an approval statement asserting no separate PRD or AD contradicted its own
lineage.

Two abandoned Task records were closed. SPEC-0058-TSK-0001 was `in-progress` and
SPEC-0058-TSK-0008 was `queued` inside a `done` Spec, and the first names the
`standaloneExecutions` entry as work it was recording: that abandoned activation
is the origin of the roster divergence, and because 0058 was never declared,
`STANDALONE-EXECUTION-STATE` could not report the unfinished Task. Both are now
`cancelled`, not `done`. Nothing shows the work completed and the records say it
did not, so the terminal state that asserts no completion is the only honest one.
`cancelled` is reachable only from `in-progress`, the same way `spec-plan` reaches
`withdrawn` only from `active`, so SPEC-0058-TSK-0008 was opened in its own commit
first rather than adding a `queued`-to-`cancelled` edge that its sibling domain
does not have. A repository-wide scan found no other terminal Spec with an
unfinished Task.

`tests/fixtures/links-and-owners.json` was retired with the dead `FIXTURE_PATH`
that pointed at it and its five registrations, including twelve line-pinned
retired-route controls. Its 504 designed mutation cases had no consumer: commit
`a8bc8c0b` removed 5313 lines from `validate-links-and-owners.py` two days
earlier, taking `_self_test` and its four fixture-context builders with them and
leaving the fixture stranded. Restoring the harness would return roughly 4900
lines to an 8000-line validator, against this Spec's own reduction goal, and the
coverage was already gone; what remained was an artifact that looked like
coverage. Retiring it completes the cleanup that refactor left half-finished.

Retiring it exposed the rest of the same residue, so the finding was
generalised rather than treated as a single file. Two sweeps were run and both
were re-run after their first form proved unreliable: a fixture sweep that
matched basenames reported seven orphans, all false once full paths were
matched, and a constant sweep that read one module at a time reported dead names
that other modules import. On the corrected sweeps every remaining fixture is
referenced by its full path, so the retired one was the only orphan, and fifteen
module constants are referenced nowhere outside the file that defines them.

Those fifteen were removed, 125 lines across eleven scripts. Ten are residue of
the same `a8bc8c0b` refactor, which touched `EXPECTED_RULE_IDS`,
`EXPECTED_ENTRYPOINTS` and `LIFECYCLE_RULE_IDS` in the commit that deleted the
self-test. Two, `WORK054_MIGRATION_SHA256` and `WORK054_SOURCE_COMMIT`, are
commit-bound constants for a completed migration, which VAL-GIC-003 names
directly. One, `EXPECTED_ARCHIVE_RECORDS`, this execution orphaned itself when
WP-003 removed its only consumer, and removing it also orphaned an import that
was removed with it.

The inventories were removed rather than repaired, and what they contained says
why. `IMPLEMENTED_RULES` listed 58 rule ids and omitted the whole
`STANDALONE-EXECUTION` family of seven, six of which predate this Spec.
`LIFECYCLE_RULE_IDS` and `EXPECTED_RULE_IDS` are two copies of one fact that had
already drifted apart by `LIFECYCLE-TERMINAL-MUTATION`, the rule that refused two
edits during this execution. An inventory nothing reads does not record which
rules exist; it records which rules someone last remembered, and repairing one
would restate a fact the emitting code already owns.
