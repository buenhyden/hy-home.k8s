# ADR-0006: cert-manager with mkcert CA as ClusterIssuer

## Overview

This ADR records the decision to introduce cert-manager as the platform's TLS certificate management component and to register the mkcert-generated rootCA as a cert-manager `ClusterIssuer` (CA type).

## Context

Platform growth (Headlamp, Istio/Kiali, Argo Rollouts Dashboard) increases the number of ingresses that need TLS.
Previously `bootstrap-local.sh` injected mkcert certificates into K8s Secrets by hand, and that burden grows with every new service.
The mkcert rootCA is already in the local trust store, so if cert-manager issues certificates from the same rootCA, every new service's TLS is trusted without extra browser setup.

## Decision

- cert-manager v1.17.x is installed through GitOps as a platform component.
- The mkcert rootCA (`secrets/certs/rootCA.pem`) is injected at bootstrap as a K8s Secret in the `cert-manager` namespace.
- A cert-manager `ClusterIssuer` of CA type is created and references that Secret.
- **New services** (Headlamp, Kiali, Argo Rollouts Dashboard) get TLS certificates through a cert-manager `Certificate` CR.
- **The existing ArgoCD** keeps the manual `argocd-local-tls` injection (to preserve behavior; it can move in a later Phase).
- ACME/Let's Encrypt is not used (unsuitable for the local hy-k8s.home.arpa domain).

## Explicit Non-goals

- ACME/Let's Encrypt integration
- Moving ArgoCD's existing TLS to cert-manager right away (a later Phase)
- Operating multiple ClusterIssuers
- Wiring Vault PKI in as a cert-manager issuer

## Consequences

- **Positive**:
  - TLS issuance for new services is automated declaratively through GitOps.
  - Trust in the mkcert rootCA extends to every certificate cert-manager issues.
  - Headlamp, Kiali, and Rollouts are reachable over HTTPS without extra browser setup.
- **Trade-offs**:
  - Bootstrap gains a step that injects the rootCA Secret.
  - ArgoCD TLS temporarily stays mixed between cert-manager and manual injection.
  - The cert-manager CRDs must be added to the AppProject clusterResourceWhitelist.

## Alternatives

### Keep manual mkcert certificate injection

- Good: simple bootstrap, no cert-manager needed
- Bad: manual work grows linearly with services, and GitOps declarativeness suffers

### Vault PKI integration

- Good: enterprise-grade PKI management
- Bad: excessive complexity for a local development environment, and extra Vault PKI setup

### Self-signed Issuer (generated by cert-manager itself)

- Good: no rootCA injection needed
- Bad: browsers do not trust it, and the local trust store must be re-registered

## Traceability

**Current-state clarification (2026-09-14).** The Decision's "`Certificate` CR"
wording no longer describes the implementation: no `kind: Certificate` manifest
exists under `gitops/` or `infrastructure/`. Headlamp, Kiali, Argo Rollouts and
adminer obtain TLS through the cert-manager ingress-shim annotation
`cert-manager.io/cluster-issuer: mkcert-ca-issuer` on each Ingress, which keeps
the mkcert `ClusterIssuer` boundary this decision chose.
